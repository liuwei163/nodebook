# Nacos / Higress 自动化与治理·能力地图

> 回答的问题：怎么让 Nacos 自动注册/发现、怎么让 Higress 自动从 Nacos 生成路由、
> 怎么做灰度，以及这些在当前环境里哪些能直接上、哪些有硬约束。
>
> 定位：**决策文档**，不写重复的操作步骤。具体命令见文末「与已有文档的关系」。
> 已全量脱敏，占位符对照表见 `README-工作空间索引.md` 第十章。
> 核对时间：2026-11-13；Nacos 3.2.1 / Higress（控制台 v2.2.5）/ HiMarket v0.8.2。

---

## 0. 一句话结论

**「自动注册」和「自动暴露路由」是两条独立链路，中间靠 Nacos 里的服务名对齐。**
当前 PoC 两条链路都是手工完成的（OpenAPI 建实例 + 控制台建 MCP 服务），
但**第 2 条只需改两个字段就能自动化**，第 1 条有三种方案且当前环境有版本约束。

| 层 | 现在 | 加什么就自动 | 产物 |
|---|---|---|---|
| 1 实例注册 | OpenAPI 手工建一条静态实例 | Nacos Controller / sidecar / SDK | Pod 上下线自动增删实例 |
| 2 路由暴露 | 控制台手工「创建 MCP 服务 → 直接路由」 | `nacosGroups` + `allowMcpServers` | `/mcp-servers/<name>` 自动生成 |
| 3 灰度治理 | 无 | 权重注解 / 版本化路径 / 工具热更新 | 按比例分流、不重启改工具 |

## 1. 先分清两类数据（最容易混的地方）

Nacos 里跟 MCP 相关的数据是**两套**，不是一套：

| | 实例数据（Naming / L1） | MCP 元数据（MCP Registry / L2） |
|---|---|---|
| 内容 | IP、端口、健康状态、权重、临时/持久 | 服务名、版本、协议类型、工具清单、参数 schema、工具描述 |
| 谁产生 | 应用实例 / K8s Service | **只有开发者能声明**，注册中心猜不出来 |
| 能不能全自动 | ✅ 可以，应用零侵入 | ❌ 不能凭空发现；只能由应用 SDK 上报或 CI/控制台登记 |
| 当前状态 | 手工 OpenAPI 注册的一条持久实例 | Nacos 控制台手工建 `mini-mcp:1.0.0`，3 个工具 |
| 消费方 | Higress 生成上游 cluster（EDS） | Higress 生成 `/mcp-servers/` 对外路由；HiMarket 本该读它（v0.8.2 缺陷，不可用） |

**这条区分解释了之前所有"配了没生效"的困惑**：
改 Nacos 的协议类型不会影响实例数据；改白名单不会影响工具清单；
HiMarket 从 Nacos 导入拿到 3 个工具来自 L2 快照，连接点却要另一套装配逻辑。

推论：**想要"工具描述热更新 / 工具运行时开关"这类治理能力，必须让应用用 SDK 自注册**——
只同步 K8s Service 或只跑 sidecar，Nacos 里永远只有 IP，没有工具清单。

## 2. 第一层：实例自动注册（三条路）

### 2.1 方案对比

| 方案 | 原理 | 是否同步工具清单 | 对应用侵入 | 当前环境可行性 |
|---|---|---|---|---|
| **A. Nacos Controller 2.0** | 官方 CRD `ServiceDiscovery`，把 K8s Service 的 Endpoints 同步成 Nacos 实例 | ❌ 只同步实例 | **零侵入** | ✅ 可上，但需 helm 装 CRD + 建凭据 Secret |
| **B. sidecar 自动注册** | 同 Pod 跑注册器，启动注册 / 心跳保活 / SIGTERM 注销 | ❌ 只注册实例 | 部署层多一个容器 | ✅ **工作区已有现成脚本**，不挑 Python 版本 |
| **C. SDK 自注册** | 应用启动时把服务定义 + `@Tool` 清单一起上报 Nacos | ✅ **唯一能带上 L2** | 要改代码 | ⚠️ 当前镜像不满足，见 2.3 |

### 2.2 官方组件要点

**Nacos Controller 2.0**（Nacos 3.0 起官方提供）：

```yaml
apiVersion: nacos.io/v1
kind: ServiceDiscovery
metadata:
  name: mcp-sd
spec:
  nacosServer:
    serverAddr: <NACOS_ADDR>
    namespace: public
    authRef:                      # Nacos 未开鉴权时可省略
      apiVersion: v1
      kind: Secret
      name: nacos-auth
  services: ["mini-mcp"]          # 省略该字段 = 同步全量 Service
```

`services` 不填会同步**全部** K8s Service，生产上务必显式列白名单。
它还支持 ConfigMap/Secret 与 Nacos 配置的双向同步，但那是配置中心能力，与本链路无关。

**sidecar**：见 `04-MCP生产化/11-nacos-register.sh`（187 行，已写好）。
关键点：用 `POD_IP` Downward API 注入、临时实例心跳保活、`trap SIGTERM` 完成注销，
避免 Pod 重建后留下摘不掉的幽灵实例。

### 2.3 ⚠️ 当前环境的硬约束（必须先知道）

官方推荐的 Python 自注册 SDK 是 `nacos-mcp-wrapper-python`
（把 `FastMCP` 换成 `NacosMCP`，工具用 `@mcp.tool()` 声明），
但它的要求是：

- Nacos Server **> 3.0.1** → 当前 3.2.1 ✅ 满足
- **Python >= 3.10** → 当前 mini-mcp 跑在 `kubeflow/python:3.7`（实测 `3.7.17`）❌ **不满足**

也就是说：**C 方案不能直接套在现在的 mini-mcp 上**。要走它，得换 ≥3.10 的镜像、
引入官方 MCP Python SDK、把手写协议实现重写成装饰器风格——等于重做一遍 MCP Server。

Java 侧对应物是 Spring AI Alibaba 的 `spring-ai-alibaba-starter-mcp-registry`
（`@Tool` + `spring.ai.alibaba.mcp.nacos.register.enabled=true`），
同样能自动注册且带工具清单，但要求应用是 Spring Boot 技术栈。

**务实选择**：当前 PoC 用 B（sidecar）拿自动注册，工具清单继续在 Nacos 控制台维护；
等真正要上多团队 MCP 市场时，再按新镜像 + SDK 重写，把 L2 一起接上。

## 3. 第二层：Higress 自动发现并生成路由

### 3.1 两个「自动发现」不是一回事

| | 订阅实例（一直都在自动） | 自动生成路由（当前是关的） |
|---|---|---|
| 开关 | `type: nacos3` + `domain/port/nacosNamespaceId` | `enableMCPServer: true` + `allowMcpServers` |
| 产物 | **上游 cluster / EDS**：网关知道去哪找后端 | **对外 HTTP 路由**：`/mcp-servers/<服务名>` |
| 当前 | ✅ 已生效——控制台「后端服务」下拉能选到 `mini-mcp::1.0.0.mcp-endpoints...` | ❌ 被控制台手工「直接路由」替代了 |

**关键认知**：传统 Nacos 服务发现**只自动生成上游，不自动生成对外路由**；
要对外访问得再写一条 Ingress 指向 `服务名.分组.命名空间.nacos`。
MCP 场景是特例——`enableMCPServer` 让网关订阅 L2 元数据，才自动铺出 `/mcp-servers/` 路径。

**这就是上一轮说的「L2 空转」**。启用白名单机制，同时补上 Nacos 版本/工具元数据的消费者，
正好把「版本管理没用起来」这个问题一起解掉。

### 3.2 字段表（实测值来自 2026-11-13 摸底）

| 字段 | 实测值 | 作用 |
|---|---|---|
| `type` | `nacos3` | Nacos 2.x/3.x；MCP 自动暴露**只支持 nacos3** |
| `enableMCPServer` | `true` | 总开关，**已开** |
| `mcpServerBaseUrl` | `/mcp-servers/` | 统一路径前缀，须以 `/` 开头结尾 |
| `mcpServerExportDomains` | 单值 | 允许的 Host；请求 Host 不匹配直接拒 |
| `nacosGroups` | `[DEFAULT_GROUP]` | ⚠️ 要补 `mcp-endpoints`，否则订阅不到 MCP 服务 |
| `allowMcpServers` | `[native-demo-mcp, openapi-demo-mcp]` | ⚠️ 白名单，不在名单里的 MCP 不生成路由 |
| `nacosNamespaceId` | `public` | **单值**；要多命名空间并存必须新增一条 registry，不能改这个 |
| `nacosRefreshInterval` | 默认 30s | 服务刷新间隔（纳秒） |
| `vport.default` | `8080` | 不参与 MCP 暴露，MCP 挂标准 80/443，别去试 8080 |

> `allowMcpServers` 在官方 `mcp-bridge` 字段表里没列全，但源码
> `api/networking/v1/mcp_bridge.proto` 有该字段，且当前集群实际配置里存在并生效。
> 语义是安全边界：**即使服务已注册进 Nacos，不在白名单里也不会被暴露成路由。**

### 3.3 最短启用步骤（下标 2 已实测确认）

```bash
# 0. 备份，必须
kubectl -n himarket get mcpbridge default -o yaml > ~/mcpbridge-backup-$(date +%Y%m%d-%H%M).yaml

# 1. 两个字段都是「整体替换」，必须把原值原样带上再追加
kubectl -n himarket patch mcpbridge default --type json -p '[
 {"op":"replace","path":"/spec/registries/2/nacosGroups",
  "value":["DEFAULT_GROUP","mcp-endpoints"]},
 {"op":"replace","path":"/spec/registries/2/allowMcpServers",
  "value":["native-demo-mcp","openapi-demo-mcp","mini-mcp","mini-mcp:1.0.0"]}]'

# 2. 别信返回值，立刻回读
kubectl -n himarket get mcpbridge default \
  -o jsonpath='{.spec.registries[2].nacosGroups}{"\n"}{.spec.registries[2].allowMcpServers}{"\n"}'
```

服务名带不带 `:1.0.0` 两份历史文档写法冲突，**一次把两种口径都加进白名单**，
URL 两种都试，避免反复 patch。完整 8 阶段（含验证/回滚）见
`02-RUNBOOK-接入Higress网关.md` 下半部——那部分此前因走了控制台路径降级为备选，
**现在正是重新启用它的场景**。

### 3.4 三个必知陷阱

1. **自动生成的路由不会出现在控制台「路由配置」列表里**（官方明确说明）。
   只能靠 curl 验证，别去列表里找，找不到不等于没生效。
2. **URL 构造规则**：`http://<mcpServerExportDomains>/<mcpServerBaseUrl>/<Nacos 中的 MCP 服务名>`。
   控制台手工「直接路由」与自动暴露共用这套前缀，注意别和已建的服务名撞车。
3. **Host 必须逐字匹配** `mcpServerExportDomains`。文档里是脱敏占位符
   `mcp.example.internal`，照抄会 403/404。且 `himarket-server` Pod 需要
   hostAliases 解析该域名（已完成，同 IP 与模型域名共用一条）。

验证（等约 30s 刷新周期后，从 `himarket-server` Pod 内发起）：

```bash
kubectl -n himarket exec deploy/himarket-server -- \
  curl -sS -m 8 -i -X POST "http://<MCP_EXPORT_DOMAIN>/mcp-servers/mini-mcp" \
  -H 'Content-Type: application/json' \
  -H 'Accept: application/json, text/event-stream' \
  -d '{"jsonrpc":"2.0","id":1,"method":"initialize","params":{"protocolVersion":"2025-03-26","capabilities":{},"clientInfo":{"name":"curl","version":"1"}}}'
```

期望 `200` + `serverInfo`。若 404，把路径换成 `mini-mcp:1.0.0` 再试。
回滚就是把备份 yaml 里那两个数组改回原值，重新 patch。

## 4. 第三层：灰度与治理

### 4.1 四级灰度

| 粒度 | 做法 | 当前可用性 | 备注 |
|---|---|---|---|
| **工具级** | Nacos 控制台改工具描述 / 关掉某个工具，运行时热生效、无需重启 | 需 SDK 自注册 | 官方自动注册手册明确支持；最轻量的"灰度"，适合先下线一个有问题的工具 |
| **实例级** | 滚动更新 1 副本，或调 Nacos 实例 `weight` | ✅ 现在可用 | `01-生产级全链路手册.md` 9.1 已写；配合健康实例自动摘除 |
| **流量级** | `higress.io/destination` 多行 `70% 服务A / 30% 服务B`，或 `canary-by-header` 注解 | ⚠️ 需实测 | 官方博客确认适用于标准 HTTP 路由，目标格式 `服务名.分组.命名空间.nacos` |
| **版本级** | Nacos 建 `mini-mcp:1.0.0` / `2.0.0` → 两条 `/mcp-servers/` 路径 → HiMarket 按产品/订阅者授权 | ✅ 现在可用 | **当前架构最确定的灰度方式**，与"多版本靠不同服务名"的结论一致 |

⚠️ **流量级的重要保留**：Higress 的 MCP 自动暴露走的是独立的
`mcp-server` golang-filter + ConfigMap 配置通道（不显示在路由列表里），
**不是标准 Ingress route**。官方没有明说 canary 注解 / `destination` 权重能否直接套在
`/mcp-servers/` 这条虚拟路由上。别把它当已验证能力写进方案，要试也是单独做对照实验。

相比之下，**版本级 + 消费者授权**这条路完全确定：不同订阅者订阅不同 HiMarket 产品，
产品绑定不同路径，等于按人群灰度，且不需要动网关权重逻辑。

### 4.2 网关治理（与灰度独立）

- **鉴权**：`key-auth` WasmPlugin，按 Consumer 授权 MCP Server 粒度访问；
  工具级权限属于企业版能力。配置模板见 `04-MCP生产化/22-higress-mcpbridge-prod.yaml`。
- **限流**：`cluster-key-rate-limit`，依赖 Redis（工作区列出的四个前置条件之一）。
- **审计/观测**：网关访问日志按服务名区分来源，配合 `registry.name` 识别注册中心。
- **Nacos 侧独有**：工具描述与参数描述热更新、工具运行时开关——这两项是
  AI Registry 相对普通注册中心的增量价值，**只有 SDK 自注册后才拿得到**。

### 4.3 版本管理什么时候才真正"有用"

启用白名单机制后，`:1.0.0` 仍只是服务名的一部分，Higress 不做版本比较、不做自动灰度。
版本要参与决策，得满足其一：

1. 不同版本用不同服务名 → 不同路径 → 调用方/产品显式选（当前可行）
2. 网关按权重或 Header 在两个服务名之间分流（需实测）
3. 治理层（MCP 市场）读 L2 元数据展示版本、描述、工具清单 → HiMarket v0.8.2 这条路是坏的

Nacos 3.3 还提供 MCP 草稿 / 审核 / 发布流程；当前 3.2.1 没有，升级前不要写进方案。

## 5. 推荐落地顺序

| 阶段 | 动作 | 成本 | 收益 | 风险 |
|---|---|---|---|---|
| **① 先开 L2 自动路由** | 3.3 的两字段 patch + curl 验证 | 2 条命令 + 30s | 让 Nacos 版本/工具元数据真正有消费者；以后新增 MCP 不必去控制台建服务 | 低，备份 + 回读即可回滚；与已验收链路平行，可并存对照 |
| **② 再上自动注册** | sidecar（`11-nacos-register.sh`）或 Nacos Controller | 半天～1 天 | Pod 重建、扩缩容不用手工改 Nacos，幽灵实例消失 | 中，涉及 Deployment 改动；建议先在新命名空间试 |
| **③ 最后治理灰度** | 版本化路径 + key-auth + 限流；按需评估 canary | 视规模 | 多团队、多版本、按人群发布 | canary 对 MCP 虚拟路由未验证；Redis 依赖 |

**如果只想验证"Nacos 到底有没有在起作用"，零改动一条命令**：

```bash
kubectl -n himarket scale deploy/mini-mcp --replicas=0
```

再在 HiChat 问一句。返回 `503 no healthy upstream` 而不是连接超时，
说明网关确实是按 Nacos 的健康实例列表判断"没上游了"。测完 `--replicas=1` 恢复。

**也可以什么都不做**：PoC 阶段通讯录够用，L2 的价值要等出现"多团队发布 MCP、
需要版本灰度、要统一管控工具描述和可见范围、要建 MCP 市场"这些需求才兑现。
阶段 ① 是唯一一个「成本极低且直接补齐上一轮缺口」的动作，推荐优先做。
