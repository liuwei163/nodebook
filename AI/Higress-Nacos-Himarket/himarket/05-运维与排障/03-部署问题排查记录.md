# HiMarket 部署问题排查记录

> 本文汇总 2026-10-27 在移动云 KCS（离线环境、私有 Harbor、共享 CLB）部署 HiMarket v0.8.2 全过程中遇到的 **28 个问题**，逐条记录现象、根因、解决方案与预防措施。
> 编号与《02-部署主手册-可复现版.md》中的 `⚠️ 坑-XX` 一一对应。
>
> **背景约束**（很多问题由这些约束放大）：
> - 完全离线，无公网出口，只能通过公司代理 `<CORP_PROXY_IP>:8080` 从摆渡机下载
> - 私有 Harbor 走 **HTTP 80**，无 TLS
> - 集群策略**禁止 NodePort**，只允许 LoadBalancer
> - 共享型 CLB，端口资源与其他业务复用，创建需审批
> - 存储只有 `local-storage`（无动态供给）

---

## 一、物料准备阶段

### 坑-01：初始化钩子全部失败，根因是架构决策

**现象**

```
[init-nacos-admin] 初始化 API 返回: HTTP 000
[init-nacos-admin] 初始化失败 (HTTP 000)，等待 10 秒后重试...
（重试 10 次全部失败，5 个钩子 4 个失败）
```

**根因**

`hooks/post_ready.d/` 里的钩子设计假设是「admin / frontend / nacos 三个 Service 都是 LoadBalancer」，因为上游 chart 默认就是：

| Service | chart 默认值 |
|---|---|
| himarket-admin | LoadBalancer |
| himarket-frontend | LoadBalancer |
| nacos | LoadBalancer |
| higress-gateway | **NodePort** |

钩子从 `status.loadBalancer.ingress[0].ip` 取 IP 再 curl。我们的架构决策是「只有网关是 LB，其余全部 ClusterIP」，于是钩子取不到 IP → 回退 `*.svc.cluster.local` → 节点上解析失败 → HTTP 000。

**解决**

用 `/etc/hosts` + `kubectl port-forward` 伪造集群内 DNS 视图，详见坑-25。

**预防**

- 部署前先明确：走「网关统一入口」就必须接受钩子需要绕行
- 如果不想折腾，代价是把 admin/frontend/nacos 也做成 LB（本项目不推荐：多 3 个 CLB、多 3 次审批、nacos 暴露）

### 坑-02：`helm pull` 拉 chart 超时

**现象**

```
Error: looks like "https://higress.io/helm-charts/" is not a valid chart repository
或
Error: Get "https://higress.io/helm-charts/higress-2.2.5.tgz": context deadline exceeded
```

但 `helm repo update` 是成功的、`curl` 同一个地址也能下。

**根因**

helm 自带 HTTP 客户端走代理时超时行为与 curl 不同（代理对 helm 的请求响应慢/被截断），`curl` 有 `--retry` 和更长 `--max-time` 反而正常。

**解决**

```bash
# 不用 helm pull，直接 curl
curl -fL --retry 3 --connect-timeout 15 --max-time 240 \
  -o charts/higress-2.2.5.tgz \
  https://higress.io/helm-charts/higress-2.2.5.tgz
```

**预防**

离线搬运统一用 `curl`，不依赖 helm 的下载能力；只用 helm 做 `template` 渲染和安装了。

### 坑-03：Higress chart 是否包含子 chart 必须验证

**现象**

如果 `charts/higress/charts/` 为空，`helm template` 或安装时报：

```
found in Chart.yaml, but missing in charts/ directory: higress-console
```

**根因**

`higress` chart 的 `Chart.yaml` 声明了两个依赖：

```yaml
dependencies:
- name: higress-core
  repository: "file://../core"              # 本地相对路径
  version: 2.2.5
- name: higress-console
  repository: "https://higress.io/helm-charts/"   # 远程仓库
  version: 2.2.5
```

其中 `higress-console` 是**远程依赖**，如果发布的 tgz 没有把依赖打包进去，离线环境无法补。

**解决**

本项目实测 `higress-2.2.5.tgz` **已包含**两个子 chart，解包验证即可：

```bash
tar xzf charts/higress-2.2.5.tgz -C /opt/charts
ls -1 /opt/charts/higress/charts/
# higress-console  higress-core
```

若缺失，需要有网环境 `helm dependency build` 或从 `higress-2.2.5` 源码包取 `helm/core`。

**预防**

搬运前把这一条作为 checklist 硬性验证项，不要等内网安装才发现。

### 坑-04：redis 镜像容易漏搬

**现象**

渲染清单里没有 `redis-stack-server`，但实际部署后有这个 Pod。

**根因**

`higress-core` 的 `global.enableRedis` 默认是 `false`；只有 `install.sh` 第 1365 行传了 `--set "higress-core.global.enableRedis=true"` 才会渲染出 Redis。

**解决**

生成镜像清单时必须带上这个参数：

```bash
helm template higress ./charts/higress -n himarket \
  --set higress-core.global.enableRedis=true | grep image:
```

**预防**

镜像清单永远用「和 install.sh 完全相同的 --set 参数」渲染，不要用 chart 默认值渲染。

### 坑-05：MySQL 镜像 tag 就是 `latest`

**现象**

`values.yaml` 里 `mysql.image.tag: "latest"`，不确定该搬哪个版本。

**根因**

chart 就是这样写的。镜像内部实际是 **MySQL 8.0.32**（Community Server）。

**解决**

```bash
docker run --rm --entrypoint mysqld <image>:latest --version
# /usr/sbin/mysqld  Ver 8.0.32 for Linux on x86_64 (MySQL Community Server - GPL)
```

在 Harbor 里额外打一个固定 tag，避免 `latest` 漂移：

```bash
docker tag .../himarket/mysql:latest .../himarket/mysql:8.0.32
docker push .../himarket/mysql:8.0.32
```

**预防**

离线环境所有镜像都应有固定 tag，`latest` 只作为兼容别名保留。

### 坑-06：Harbor 是 HTTP，docker 必须配 insecure-registries

**现象**

```
Error response from daemon: http: server gave HTTP response to HTTPS client
```
或 `ImagePullBackOff`，事件里同样报 HTTPS/HTTP 协议错误。

**根因**

Harbor 只有 80 端口、无 TLS。docker/containerd 默认用 HTTPS 访问 registry。

**解决（摆渡机/构建机）**

```bash
# /etc/docker/daemon.json
{
  "insecure-registries": ["harbor.example.internal", "harbor.example.internal:80"]
}
systemctl restart docker
```

**解决（集群节点）**

KCS 托管集群不能直接改节点 containerd 配置，需在云平台控制台配置私有镜像仓库/insecure registry，或提交工单。

**验证**

```bash
kubectl run pulltest -n himarket --rm -it --restart=Never \
  --image=harbor.example.internal/ai-platform/himarket/himarket-server:v0.8.2 \
  --overrides='{"spec":{"imagePullSecrets":[{"name":"harbor-secret"}]}}' -- true
```

### 坑-07：`docker login` 报 503，根因是代理

**现象**

```
Error response from daemon: login attempt to http://harbor.example.internal/v2/ failed
with status: 503 Service Unavailable
```

但同一台机器 `curl -u user:pass http://harbor.example.internal/v2/` 返回 200。

**根因**

docker daemon 配了公司代理（`http-proxy: http://<CORP_PROXY_IP>:8080`），而 `no-proxy` 里**没有 Harbor 域名**。于是内网 Harbor 的请求被转发到公司代理，代理访问不了内网地址，返回 503。

curl 之所以正常，是因为那次 curl 没走代理（或走了带内网路由的路径）。

**解决**

`/etc/docker/daemon.json` 的 `proxies.no-proxy` 加上 Harbor：

```json
{
  "proxies": {
    "http-proxy": "http://<CORP_PROXY_IP>:8080",
    "https-proxy": "http://<CORP_PROXY_IP>:8080",
    "no-proxy": "localhost,127.0.0.1,<WSL_SUBNET>/20,harbor.example.internal,.example.internal"
  }
}
```

重启 docker 后 `Login Succeeded`。

**预防**

凡是「外网走代理 + 内网直连」的机器，`no-proxy` 必须包含全部内网域名/IP 段。排查时用 `curl -x <proxy>` 与 `curl --noproxy '*'` 对比，能快速定位。

## 二、集群准备阶段

### 坑-08：secret 建好但 Pod 拉不到镜像——独立 ServiceAccount

**现象**

```
pod/himarket-admin    0/1  ImagePullBackOff
pod/mysql-0           0/1  ImagePullBackOff
```

但手工 `kubectl run --overrides` 注入 secret 就能拉取成功。

**根因**

1. secret 建了，但没挂到 ServiceAccount 上；
2. 挂了 `default` SA 也没用 —— 这个 chart 用的是**独立 SA**：

```bash
kubectl get pod -n himarket -o jsonpath='{range .items[*]}{.metadata.name}{" -> "}{.spec.serviceAccountName}{"\n"}{end}'
# himarket-admin     -> SA=himarket
# himarket-server    -> SA=himarket
# sandbox-shared     -> SA=default
```

**解决**

```bash
for sa in himarket default higress-gateway higress-console higress-controller; do
  kubectl patch sa "$sa" -n himarket --type merge \
    -p '{"imagePullSecrets":[{"name":"harbor-secret"}]}' 2>/dev/null
done
```

**预防**

部署前先确认 chart 用的是哪个 SA（`values.yaml` 里的 `serviceAccount.name`），不要假设是 `default`。

---

### 坑-09：helm 回滚会删掉 chart 创建的 ServiceAccount

**现象**

第一次安装失败回滚后，重新 `helm install`，Pod 又全部 `ImagePullBackOff`。

**根因**

SA 是 chart 资源的一部分，`--atomic` 回滚 / `helm uninstall` 会连带删除 SA。重新安装时 SA 是新建的，`imagePullSecrets` 为空。

**解决**

重装后立刻重新执行坑-08 的 patch。

**预防**

把「重装后补 SA」写进运维约定（手册第 10 章）。长期方案是在 `values.yaml` 里直接配 `imagePullSecrets`，但 gateway/console 的模板不一定支持该字段（本项目实测 gateway 渲染出来是 `None`），所以 SA patch 仍是最可靠手段。

---

### 坑-10：patch 了 SA 但 Pod 还是拉不到

**现象**

SA 已经显示 `[{"name":"harbor-secret"}]`，Pod 依旧 `ImagePullBackOff`。

**根因**

`imagePullSecrets` 是 Pod 创建时从 SA 固化的，**改 SA 不影响已存在的 Pod**。

**解决**

```bash
kubectl delete pod -n himarket --all
# 或只删失败的
kubectl get pods -n himarket --no-headers | awk '/higress-gateway|higress-console/{print $1}' | xargs -r kubectl delete pod -n himarket
```

**预防**

patch SA 和删 Pod 必须成对操作。

---

### 坑-11：`local-storage` 是 no-provisioner，PVC 永远 Pending

**现象**

```
NAME               STATUS    VOLUME   CAPACITY   ACCESS MODES   STORAGECLASS
mysql-data-mysql-0 Pending                                      local-storage
```

**根因**

```bash
kubectl get sc
# local-storage  kubernetes.io/no-provisioner  WaitForFirstConsumer
```

`no-provisioner` 表示没有动态供给器，必须**预先创建容量/类型匹配的 PV** 才能绑定。

**解决**

按手册 2.5 节创建 2 个静态 PV（hostPath + DirectoryOrCreate + nodeAffinity）。

**为什么不装 local-path-provisioner**

需要额外搬运 provisioner + helper 两个镜像，且仍然是节点本地盘，收益低。静态 PV 更省事。

---

### 坑-12：PV 的 nodeAffinity 填成 master，Pod 永远调度不上

**现象**

PV `Available`，PVC 仍 `Pending`，mysql 一直 `Pending`。

**根因**

master 节点带 `node-role.kubernetes.io/control-plane:NoSchedule` 污点，即使 PV 的 nodeAffinity 指向它，Pod 也不会被调度过去。

**解决**

```bash
kubectl get pv -o jsonpath='{range .items[*]}{.metadata.name}{" -> "}{.spec.nodeAffinity.required.nodeSelectorTerms[0].matchExpressions[0].values[0]}{"\n"}{end}'
# 必须是 s-xxx（worker），不能是 m-xxx（master）

# 已写错可用 patch 修正
kubectl patch pv himarket-mysql-pv --type json \
  -p '[{"op":"replace","path":"/spec/nodeAffinity/required/nodeSelectorTerms/0/matchExpressions/0/values/0","value":"<HIMARKET_NODE_WORKER2>"}]'
```

**预防**

创建 PV 前先 `kubectl get nodes -l '!node-role.kubernetes.io/control-plane'` 拿 worker 列表。

---

### 坑-13：两个 PVC 交叉绑定到对方的 PV

**现象**

```
persistentvolumeclaim/mysql-data-mysql-0      Bound  himarket-sandbox-pv
persistentvolumeclaim/sandbox-workspace-pvc   Bound  himarket-mysql-pv
```

**根因**

两个 PV 的 `capacity/storageClassName/accessModes` 完全一样，调度器按到达顺序任意匹配，不看 PV 名字。

**影响**

功能上无影响（同节点、同容量、都是空目录），但 **MySQL 真实数据落在 `/var/lib/paascontainer/himarket/sandbox`**，备份/排障容易搞反。

**解决**

本次选择不处理（重来成本高于收益），只在文档中明确记录实际对应关系。

彻底避免的办法是给 PV 加 `claimRef` 预绑定：

```yaml
spec:
  claimRef:
    namespace: himarket
    name: mysql-data-mysql-0
```

**预防**

同规格多 PV 的场景，一定要用 `claimRef` 或给 PV 打不同的 storageClass，否则绑定顺序不可控。

## 三、操作机与配置改造阶段

### 坑-14：helm 版本冲突

**现象**

集群侧已有 `helm v3.15.3`，又装了 `v3.22.1` 到 `/usr/local/bin`。

**根因**

`/usr/local/bin` 在 PATH 中通常优先于 `/usr/bin`，导致实际用的是新版本，行为不一致、排查困难。

**解决**

只保留系统自带的 `v3.15.3`（满足 chart 要求），不要额外安装。

**预防**

部署前先 `helm version --short` 确认版本，够用就不动。

---

### 坑-15：改 `values.yaml` 的镜像地址完全不生效

**现象**

把 `hub` 改成 Harbor 后安装，Pod 仍去拉 `opensource-registry.cn-hangzhou.cr.aliyuncs.com`。

**根因**

`install.sh` 有三处会覆盖 values：

1. 第 611 行 `unset HIMARKET_HUB HIMARKET_IMAGE_TAG ...` —— 连 env 文件里的值都清掉
2. 第 818 行 `HIMARKET_HUB="${HIMARKET_HUB:-opensource-registry...}"` —— 默认值写死公网
3. 第 1296 行 `--set "hub=${HIMARKET_HUB}"` —— `--set` 优先级高于 values.yaml

**解决**

必须改 **install.sh 里的默认值**（手册 4.2 节），而不是 values.yaml。

**预防**

理解 `--set > values.yaml > chart 默认值` 的优先级链，同时注意脚本可能在中间 `unset` 环境变量。

---

### 坑-16：注释掉 `helm repo` 导致 bash 语法错误

**现象**

```
install.sh: line 1258: syntax error near unexpected token `}'
install.sh: line 1258: `}'
```

**根因**

`add_repos()` 函数体只有两行 `helm repo add/update`。全部用 `#` 注释后函数体为空：

```bash
add_repos() {
    # [offline] helm repo add ...
    # [offline] helm repo update ...
}
```

bash 的**函数体不能为空**（只允许注释也会报错）。

**解决**

用 `:`（no-op 命令）替代纯注释：

```bash
add_repos() {
    : # [offline] helm repo add ... --force-update
    : # [offline] helm repo update ...
}
```

**预防**

disable 某段脚本时，永远保留至少一条 `:`，并用 `bash -n` 验证。

### 坑-17：`higress-console` 镜像不受 `global.hub` 控制

**现象**

渲染结果里其他 higress 镜像都指向 Harbor，唯独 console 还是阿里云：

```
harbor.example.internal/ai-platform/higress/gateway:2.2.5
higress-registry.cn-hangzhou.cr.aliyuncs.com/higress/console:2.2.5   ← 漏了
```

**根因**

`higress-console` 是独立子 chart，有自己的 `hub` 字段（默认 `""`，会回落到父 chart 的 `global.hub`，但我们的 patch 只改了 `higress-core`）。

**解决**

单独改 `charts/higress/charts/higress-console/values.yaml` 里的 registry 字面量。

**预防**

渲染核对时必须逐个检查镜像前缀，不要只看数量。

---

### 坑-18：`sandbox` 镜像 tag 脚本根本不传

**现象**

渲染出 `harbor.example.internal/ai-platform/himarket/sandbox:`**`latest`**，而 Harbor 里只有 `v0.8.2`。

**根因**

`install.sh` 的 `--set` 列表里只有：

```
frontend.image.tag / admin.image.tag / server.image.tag / mysql.image.tag
```

**没有 `sandbox.image.tag`**，所以只能用 values.yaml 的默认值 `latest`。

**解决**

改 `himarket/values.yaml` 里 `sandbox.image.tag` 为 `v0.8.2`。

**预防**

凡是脚本不传的字段，只能靠 values；改完必须渲染确认。

## 四、部署执行阶段

### 坑-19：mysql 日志出现 `Received SHUTDOWN` 很吓人，其实是正常流程

**现象**

```
[Entrypoint] MySQL init process done. Ready for start up.
[System] [MY-013172] Received SHUTDOWN from user root. Shutting down mysqld
[Entrypoint] Server shut down
[Entrypoint] Starting MySQL 8.0.32-1.2.11-server
[System] ready for connections. port: 3306
```

**根因**

官方 mysql 镜像首次启动会先 `--initialize` 建 datadir，完成后关闭实例，再正式启动。这是设计行为。

**解决**

无需处理。判断就绪看最后一行 `ready for connections`，以及 `kubectl get pod` 的 READY 变 `1/1`。

**预防**

不要看到 `SHUTDOWN` 就以为 Pod 崩了，看时间线和最终状态。

---

### 坑-20：Pod `ImagePullBackOff` 的通用排查顺序

**排查顺序（建议固化）**

```bash
# 1. 用的哪个 SA？
kubectl get pod -n himarket <pod> -o jsonpath='{.spec.serviceAccountName}'

# 2. SA 有没有挂 secret？
kubectl get sa -n himarket <sa> -o jsonpath='{.imagePullSecrets}'

# 3. 事件里具体报什么？
kubectl describe pod -n himarket <pod> | grep -A5 'Failed\|Events'

# 4. 网络/协议问题
kubectl run pulltest ... --overrides 注入 secret 测试
```

常见错误对照：

| 事件关键字 | 原因 |
|---|---|
| `401 Unauthorized` / `pull access denied` | SA 没挂 secret，或 secret 的 server 字段不匹配 |
| `http: server gave HTTP response to HTTPS client` | 节点不认 HTTP registry（insecure 未配） |
| `no such host` | 节点 DNS 解析不了 Harbor 域名 |
| `manifest unknown` | tag 不存在（例如用了 `latest` 但 Harbor 里没有） |

### 坑-21：`install.sh` 的 `--wait --atomic` 会因等不到 LB IP 而整体回滚

**现象**

```
[HiMarket 09:53:14] 安装/升级 higress (第 1/3 次)...
Error: release higress failed, and has been uninstalled due to atomic being set:
context deadline exceeded
[HiMarket 10:13:15] higress 安装失败（第 1 次），准备重试
[HiMarket 10:13:23] 安装/升级 higress (第 2/3 次)...
```

每轮 900 秒，共 3 轮，最后整包回滚。

**根因**

`helm upgrade --install --wait --atomic` 的 `--wait` 不只等 Pod Ready，**也会等 `type: LoadBalancer` 的 Service 拿到 `status.loadBalancer.ingress`**。共享 CLB 监听器冲突/审批中，IP 一直不来 → 超时 → `--atomic` 回滚。

**解决**

1. 先停脚本（顺序重要，先杀 helm 再杀脚本，否则 helm 继续持有锁）：

```bash
pkill -f 'helm upgrade'
pkill -f 'install.sh'
```

2. 清 pending 状态：

```bash
helm list -n himarket --all
helm uninstall higress -n himarket
```

3. 用**不带 `--wait`** 的命令单独装 higress（手册 5.4 节）。

**预防**

- 离线 + 共享 CLB 的环境，`--wait` 是负担：Pod 已经 Ready，只是 LB 迟迟不给 IP
- 日常升级一律用不带 `--wait` 的 `helm upgrade`，不要用 `install.sh` 全量跑

### 坑-22：helm 报 `another operation is in progress`

**现象**

```
Error: UPGRADE FAILED: another operation (install/upgrade/rollback) is in progress
```

**根因**

前一次 `helm install/upgrade` 被中断（脚本被 kill、SSH 断开等），release 状态停在 `pending-install` / `pending-upgrade`，锁未释放。

**解决**


**预防**

## 五、网关与 CLB 阶段

### 坑-24：共享 CLB 端口被历史监听器占用

**现象**

`kubectl get svc` 里 `EXTERNAL-IP` 永远 `<pending>`，CCM 日志：

```
E controller.go:353] error processing service himarket/higress-gateway
(retrying with exponential backoff): failed to ensure load balancer:
failed to sync listeners: failed to ensure listener for port 30080:
port 30080 is already in use by listener Listener_himarket_poc30080
```

同时 Service 事件：

```
Warning SyncLoadBalancerFailed  Error syncing load balancer:
... port 30080 is already in use by listener Listener_himarket_poc30080
```

**根因**

共享 CLB（`isExclusive: false`，上面挂着十几个其他业务监听器）上，30080 端口已被一个**手工创建的监听器**占用。CCM 的行为是「创建并管理自己的监听器」，**不会复用**已存在的监听器，因此每次都失败。

**三种解法**

| 方案 | 做法 | 优点 | 缺点 |
|---|---|---|---|
| A | 删掉手建监听器，让 CCM 托管 | Service 状态正确、`--wait` 可用、后端池自动维护 | 删除时秒级中断；需要云平台权限 |
| B | 保留手建监听器，直接用 CLB VIP 访问 | 不动集群、立刻可用 | Service 永远 pending、`--wait` 不可用、扩缩容手工维护后端池 |
| C | 换一个空闲端口（如 30081/30444） | 避开冲突 | 要确认新端口也没被占 |

**本项目采用方案 B**，原因：监听器是业务方自己创建的，CLB 走审批流程、变更成本高；且业务已可用。

**方案 B 的操作要点**

```bash
# 确认监听器已存在且后端池指向 3 个 worker 的 30080
# 直接用 VIP 访问验证
curl -I http://<MODEL_GW_IP>:30080/
# 返回 200 + server: istio-envoy 即通
```

**预防**

- 在共享 CLB 上部署前，先列出已有监听器端口（`Listener_xxx_<port>` 命名规律很明显），避开已占用端口
- 若追求自动化运维，长期应走方案 A

## 六、初始化钩子阶段

### 坑-25：钩子报 `HTTP 000`（DNS 解析失败）

**现象**

```
[init-nacos-admin 10:41:57] 未检测到 LoadBalancer IP，使用 ClusterIP 模式
[init-nacos-admin 10:41:57] 初始化 URL: http://nacos.himarket.svc.cluster.local:8080/v3/auth/user/admin
[init-nacos-admin 10:41:58] 初始化 API 返回: HTTP 000
```

**根因**

1. 钩子**在操作机本地用 bash 执行**，网络视角是宿主机，不是集群内
2. 钩子取址逻辑：`kubectl get svc <name> -o jsonpath='{.status.loadBalancer.ingress[0].ip}'`，ClusterIP 类型没有该字段 → 空
3. 回退到 `*.svc.cluster.local`，这是 CoreDNS 提供的**集群内部域名**，只对 Pod 有效
4. 宿主机 `/etc/resolv.conf` 里没有这个域 → curl DNS 失败，退出码 6 → `%{http_code}` 输出 `000`

**解决**

`/etc/hosts` 把三个内部域名指到不同回环 IP + `port-forward` 绑到对应 IP，伪造 DNS 视图（手册 7.2 节）：

```bash
cat >> /etc/hosts <<'EOF'
127.0.0.2 himarket-admin.himarket.svc.cluster.local
127.0.0.3 himarket-frontend.himarket.svc.cluster.local
127.0.0.4 nacos.himarket.svc.cluster.local
EOF

kubectl -n himarket port-forward --address 127.0.0.2 svc/himarket-admin    80:80   >/tmp/pf-admin.log 2>&1 &
kubectl -n himarket port-forward --address 127.0.0.3 svc/himarket-frontend 80:80   >/tmp/pf-front.log 2>&1 &
kubectl -n himarket port-forward --address 127.0.0.4 svc/nacos            8080:8080 >/tmp/pf-nacos.log 2>&1 &
```

然后 `./install.sh --init-data`。

**为什么不用其它方案**

| 方案 | 不可行的原因 |
|---|---|
| 把 Service 改 NodePort | NodePort 同样没有 `status.loadBalancer`，钩子照样回退 DNS |
| 把 Service 改 LoadBalancer | 要额外建 3 个 CLB + 3 次审批，且暴露 nacos |
| 改钩子加 env 覆盖 | 可行（`65-sync-nacos-market.sh` 自带 `HIMARKET_API_URL`），但升级会覆盖脚本改动 |

**预防**

- 跑完钩子立刻清理 hosts 与 port-forward，否则以后在节点上解析这些域名会指向 127.0.0.x，误导排障
- 把这三条命令沉淀进运维手册，重装时直接复制

## 七、访问验证阶段

### 坑-27：两个域名返回完全相同的页面（命中兜底路由）

**现象**

```bash
curl -I -H "Host: himarket-admin.example.internal" http://<MODEL_GW_IP>:30080/   # 200, 5130 字节
curl -I -H "Host: himarket.example.internal"       http://<MODEL_GW_IP>:30080/   # 200, 5130 字节
```

两个域名返回**一模一样**的内容，看起来像"都正常"，其实是错的。

**根因**

```bash
kubectl get ingress -n himarket
# NAME      CLASS      HOSTS   ADDRESS   PORTS
# default   himarket   *                 80,443     ← chart 自带的兜底路由
```

没有建 Host 路由时，所有请求都命中 `HOSTS: *` 的兜底 Ingress。

**解决**

建立两条 Host 路由后，响应应变成不同大小（本项目：1926 / 2354 字节）。

**预防**

判断 Ingress 是否生效，**不要只看 HTTP 200**，要比对响应内容/大小是否随 Host 变化。确认业务正常后可删除兜底路由：

```bash
kubectl delete ingress default -n himarket
```

## 八、模型对话与输出阶段

> 前七章到「能打开页面」为止。这一章是「能打开」之后才暴露的坑：
> 模型能对话、工具也能调，但回复质量异常。这类问题的特点是**报错信息完全指不出根因**。

### 坑-29：正文里裸露 `<think>`，回复说到一半就断

**现象**

HiChat 里能看到两个可折叠的「思考过程」区域是正常的，但正文里混进一段裸标签：

```
<think>好的，用户之前请求查看当前时间，我需要调用获取时间的函数……现在收到了响应，显示当前时间是
```

正文在「显示当前时间是」这里**戛然而止**，后面本该跟具体时间却没有。

**根因**

不是 reasoning parser 配错，是**生成被 `max_tokens` 截断**。因果链：

```
思考太长 → 撞上 max_tokens 上限 → 生成中断 → </think> 没有输出
        → parser 找不到闭合标签 → 无法切分 → 整段（含 <think>）当 content 返回
```

`--reasoning-parser qwen3` 靠**成对的** `<think>`…`</think>` 定位边界。只看到开始标签、没看到结束标签时，
它无法判断这段到底属于思考还是正文，只能保守地整段当正文返回——**不报错、不打日志，完全静默**。

真正的上限在 **HiMarket 产品配置**里，不在 vLLM 启动参数里：

| 层 | 参数 | 限制什么 | 本次实测值 |
|---|---|---|---|
| **HiMarket 产品层** | 产品详情 →「最大输出 Tokens」 | 单次输出上限（= 请求体 `max_tokens`） | **500 ← 瓶颈在这** |
| vLLM 服务层 | `--max-model-len` | 输入 + 输出总长 | 32768（够用） |
| vLLM 调度层 | `--max-num-batched-tokens` | 单批调度上限，**与输出长度无关** | 16384（名字有误导性） |

500 token 约等于 350~400 个汉字。第一轮思考 + `tool_calls` 的结构化 JSON 就接近用完，
第二轮（收到工具结果后重新推理，比第一轮更长）必然写不完思考和答案。

**解决**

产品详情 → 改配置（**不用重启任何 Pod**）：

| 字段 | 改前 | 改后 | 理由 |
|---|---|---|---|
| 最大输出 Tokens | 500 | `4096` | 给思考留足空间，最优先 |
| 温度 | 0.9 | `0.3~0.5` | 工具调用要稳定；温度高容易把参数编错，甚至写坏 `tool_calls` 的 JSON |

保存后**重开一个对话**再测——旧对话历史里已经混进残缺的 `<think>` 文本，会干扰模型对新一轮格式的判断。

如果 4096 之后仍然截断，说明 HiChat 侧把 `max_tokens` 写死了，这时才动 vLLM，加一条：

```yaml
--default-chat-template-kwargs '{"enable_thinking": false}'
```

模板不再输出 `<think>`，「思考吃预算」这个问题从源头消失。**工具调用不受影响**——
那是 `--tool-call-parser hermes` 的职责，与 thinking 是两套独立机制。

**预防**

`finish_reason` 是唯一可靠的判据：`length` = 被截断，`stop` = 正常结束。
只要看到 `length`，就不要再怀疑 parser，直接查最上面那层（产品配置）。
最容易忽略的也正是它——它在界面上，不在 vLLM 启动参数里。

### 坑-30：换了 parser 名、调了 `--max-model-len`，全都无效

**现象**

同一个问题按三条思路各试一遍，行为毫无变化：

1. 怀疑 `--reasoning-parser` 名字写错 → 确认为 `qwen3`（并未写错）
2. 改成 `deepseek_r1` 试 → 回复内容全空（更糟，因为标签格式不匹配）
3. 把 `--max-model-len` 从 32768 提到 40960 → 重启 Pod，症状一模一样

**根因**

三次修改都落在**错的层**上：

- `--reasoning-parser qwen3` 本来就是对的值，改它等于没改
- `--max-model-len` 管的是「输入 + 输出」的总额度，**不是输出上限**。
  输出上限由请求里的 `max_tokens` 决定，而 HiChat 的 `max_tokens` 来自 HiMarket 产品配置，vLLM 侧改不动。

**怎么提前判断该动哪一层**

一个一分钟就能做完的对照实验：**用直连模型的客户端（Chatbox 等）问同样的问题**。

| 结果 | 结论 |
|---|---|
| 直连不截断，经 HiMarket 就截断 | 100% 是产品层配置，与 vLLM 无关 |
| 两边都截断 | 才轮到查 vLLM 或客户端自身的 `max_tokens` |

**预防**

遇到「输出被截断」先数一遍有几层能限制输出长度，从**最上层、改动成本最低**的那层查起：

```
HiMarket 产品配置（界面，改完即生效）
    ↓ 不够再往下
客户端自己的 max_tokens（Chatbox 等）
    ↓
vLLM --max-model-len（要重启，且改的往往不是地方）
```

`--max-num-batched-tokens` 完全不用看，它跟单次输出长度没有关系。

## 复盘：如果重来一次，可以提前避开的

1. **动手前先确认 4 件事**：StorageClass 是否动态供给、CLB 允许哪些端口、集群是否禁 NodePort、Harbor 是否 HTTP——这 4 个决定了整个方案形态。
2. **镜像清单用 install.sh 同参渲染**，不要用 chart 默认值，否则会漏 redis、错 tag。
3. **改配置只改 install.sh 的默认值**，因为脚本会 `unset` + `--set`，改 values 全是白工。
4. **部署前先把 SA 的 imagePullSecret 配好**，能省掉两轮 `ImagePullBackOff` 排查。
5. **给 higress 单独用不带 `--wait` 的安装方式**，避免 45 分钟的三轮超时等待。
6. **初始化钩子提前准备好 hosts + port-forward**，不要等部署跑到最后一步才发现连不上。
7. **模型能对话之后，先检查产品层的「最大输出 Tokens」**。默认 500 会让 Qwen3 的思考链把预算耗尽，
   表现为正文裸露 `<think>`、回答说到一半就断。这个值在 HiMarket 界面上、不在 vLLM 启动参数里，
   最容易找错地方（坑-29 / 坑-30）。
