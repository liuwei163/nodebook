**自动化的三层结论**（详见能力地图）：

| 层 | 现在 | 加什么就自动 |
|---|---|---|
| 实例注册 | OpenAPI 手工建静态实例 | Nacos Controller `ServiceDiscovery` CRD / sidecar / SDK 自注册 |
| 路由暴露 | 控制台手工「创建 MCP 服务 → 直接路由」 | `nacosGroups` 补 `mcp-endpoints` + `allowMcpServers` 加服务名（下标 2 已实测） |
| 灰度治理 | 无 | 实例 weight / 版本化路径 + 订阅者授权（已可用）；`destination` 权重需实测 |

⚠️ **当前环境硬约束**：官方 Python 自注册 SDK `nacos-mcp-wrapper-python` 要求 **Python ≥ 3.10**，
而 mini-mcp 跑在 `kubeflow/python:3.7`（3.7.17）→ SDK 方案用不了，需换镜像重写；
务实选择是已有的 `04-MCP生产化/11-nacos-register.sh` sidecar（只注册实例，不同步工具清单）。
另外「工具描述热更新 / 工具运行时开关」属 Nacos L2 能力，只有 SDK 自注册后才拿得到。

**落地前置条件**（四个都缺一不可）：

1. 能往 Harbor 推自建镜像
2. Nacos 有建 `ai-mcp` 命名空间的权限
3. 有可用的 `mcp-prod.example.internal` 域名解析
4. 有 Redis（限流插件依赖）

**为什么不直接上生产方案**：`22-higress-mcpbridge-prod.yaml` 是整体声明式的，`apply` 会覆盖整个 `registries` 数组。执行前必须先 `kubectl get mcpbridge default -o yaml > backup.yaml` 备份。
