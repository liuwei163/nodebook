## 第一篇　服务注册与发现（#1–#9）

> 运维基础盘。注册中心是后面所有链路故障的判定起点；#9（namespace / group / cluster）也是 AI 平台配 Nacos 时最容易填错的一题，属两岗共用。

### 1. 为什么需要注册中心？硬编码服务地址有什么问题？★★★【公认】

> 母版 #1　｜　岗位：`S`

**答**：硬编码 IP 在实例动态变化时是灾难——扩容要改所有调用方配置并发布，实例宕机无法自动摘除，流量会持续打到死地址。注册中心把「服务名 → 实例列表」的映射集中管理：提供者启动时注册，消费者按名查询或订阅，实例上下线由注册中心推送变更。

**加分**：说清三个动作 —— 注册、发现、变更通知；再补一句"消费者通常有本地缓存，注册中心短暂不可用不至于全站瘫痪"。

### 2. 一次完整的服务注册与调用流程是怎样的？★★★【公认】

> 母版 #2　｜　岗位：`S`

**答**：① Provider 启动，把服务名 / IP / 端口 / 元数据注册到注册中心；② 建立心跳或长连接保活；③ Consumer 启动，按服务名拉取并订阅实例列表，缓存到本地；④ 请求时用负载均衡策略挑一个实例发起调用；⑤ Provider 下线，注册中心剔除实例并推送变更，Consumer 更新缓存。

**易错**：别漏掉「订阅 + 推送」和「本地缓存」，这两处是面试官判断你有没有真用过的关键。

### 3. CAP 定理是什么？为什么注册中心多半选 AP？★★★【公认】

> 母版 #4　｜　岗位：`S`

**答**：分布式系统在分区容错 P 前提下，一致性 C 与可用性 A 不可兼得。注册中心的职责是「让调用方能拿到一份可用实例列表」，网络分区时返回一份稍旧的列表，业务还能继续跑；若选 CP 强一致，选主期间拒绝服务，所有调用直接拿不到地址，故障被放大。所以服务发现普遍偏 AP。

**加分**：指出 Nacos 不是"整体 AP 或整体 CP"，而是**按数据类型分路径**：临时实例走偏 AP 的 Distro，持久实例和需要强一致的数据走偏 CP 的路径（Distro/Raft 细节见《面试-补充-后端开发》#3）。

### 4. Nacos、Eureka、Consul、ZooKeeper 怎么对比？★★★【官方 + 公认】

> 母版 #5　｜　岗位：`S`

| 维度 | Nacos | Eureka | Consul | ZooKeeper |
|---|---|---|---|---|
| CAP | 临时实例偏 AP，持久实例偏 CP，**两种并存** | AP | CP（Raft） | CP（ZAB） |
| 健康检查 | 客户端心跳 + 服务端主动探测（TCP/HTTP/MySQL） | 客户端心跳 | 丰富（TCP/HTTP/Script） | Session 心跳 |
| 配置中心 | ✅ 内置 | ❌ | ✅ KV | ❌（需自行实现） |
| 控制台 | 功能完整 | 简陋 | 有 | 无 |
| 维护状态 | 活跃（3.x 持续演进） | 2.x 已停止维护 | 活跃 | 活跃（主要用于协调，非专职注册中心） |

**加分**：Nacos 的差异化是"注册 + 配置一体"、保护阈值、权重与元数据、以及 3.x 起同时是 **AI Registry（MCP / Prompt / A2A）**。Eureka 已停更，面试别再答"新项目选 Eureka"。

### 5. Nacos 临时实例和持久实例有什么区别？★★★【官方】

> 母版 #6　｜　岗位：`S`

**答**（按 3.x 官方表述）：

| | 临时服务（ephemeral） | 持久服务 |
|---|---|---|
| 状态由谁维护 | 存活的客户端 | 服务端持久化路径 |
| 健康检查 | gRPC SDK 靠连接生命周期；HTTP 客户端靠心跳续约 | 服务端主动探测（TCP / HTTP / MySQL / NONE） |
| 失效后 | 连接断开 / 心跳过期即被移除 | 不自动删，可从服务端 snapshot 恢复 |
| 一致性路径 | 偏 AP，Distro 同步 | 偏 CP，写入失败**不会**回退到 Distro |

⚠️ **两个高频扣分点**：
- `ephemeral` 是 **Service 级语义**，同一个 Service 下**不能混用**临时和持久实例（2.0 起）。
- 持久实例**不是**"不做健康检查的临时实例"，它走服务端的主动探测。

### 6. Nacos 心跳与健康检查的细节？★★★【官方 + 公认】

> 母版 #7　｜　岗位：`S`

**答**：临时实例由客户端保活。gRPC SDK 客户端把实例挂在连接上，连接断开服务端即清理该连接的 publisher/subscriber 状态，重连后 SDK 靠 redo 数据重新注册；HTTP/兼容客户端靠心跳续约，Nacos 3.x 的 HTTP OpenAPI 里注册与续约是**同一个接口**，用 `heartBeat=true` 表示续约。续约只声明"还活着"，**不会重新解析完整元数据**；实例已被过期删除就必须重新完整注册。

**【公认】常见默认值**：心跳 5s、15s 未收到标为不健康、30s 剔除。但 3.x 官方用保留元数据键配置这些时长 —— `preserved.heart.beat.interval`、`preserved.heart.beat.timeout`、`preserved.ip.delete.timeout`。**答题时说"默认常见 5/15/30，实际可用元数据调整"最稳**，别把数字说成不可变的硬编码。

### 7. `healthy` 和 `enabled` 有什么区别？★★【官方｜拉开差距的题】

> 母版 #8　｜　岗位：`S`

**答**：
- `healthy`：实例当前是否健康，来自心跳、健康检查器或节点同步 —— **系统判定**。
- `enabled`：是否允许被消费者选中，由运维通过控制台 / Admin API 修改 —— **人工开关**（常用于优雅上下线）。

被禁用的实例不会返回给运行时消费者，Java SDK 选择时也会过滤。**排查"实例存在但发现不到"时，先查 `enabled`、`healthy`、cluster 过滤、保护阈值这四项。**

### 8. 注册中心整个集群挂了，服务之间还能调通吗？★★★【公认】

> 母版 #12　｜　岗位：`S`

**答**：短时可以。消费者本地缓存了实例列表，已建立的调用不依赖注册中心；注册中心不可用期间**无法感知新上线和下线**，所以会出现"流量打到已下线实例"或"新实例接不到流量"。恢复后靠重新订阅与推送收敛。

**加分**：这正是 AP 设计与客户端缓存 failover 的意义；同时说明生产仍要部署 3 节点以上集群、配多个 `server-addr`、并配好健康检查与熔断兜底。

### 9. Nacos 的 namespace / group / service / cluster / instance 各自隔离什么？★★【官方】

> 母版 #13　｜　岗位：`S+A`

**答**：资源模型是 `namespaceId → groupName → serviceName → clusterName → instance`。Namespace 隔离环境/租户/业务域；Group 在命名空间内继续分组（默认 `DEFAULT_GROUP`）；Service 是服务发现单元，消费者按服务名查实例；Cluster 常用于机房/区域划分；Instance 是具体 IP + 端口 + 元数据。

**易错**：`nacosNamespaceId` 要填**命名空间 ID 而不是名称**；`public` 是默认命名空间 ID。

## 第二篇　网关与流量治理（#10–#16）

> 重点是三者别答混：限流 / 熔断 / 降级；以及「服务发现只生成上游、不生成对外路由」。#16 灰度策略要能顺带讲出放量与回滚。

### 10. 为什么需要 API 网关？和 Nginx 有什么区别？★★★【公认】

> 母版 #14　｜　岗位：`S`

**答**：服务拆多之后，前端不可能知道每个服务的地址，鉴权/限流/日志又会在每个服务里重复实现。网关提供统一入口、路由、鉴权、限流、熔断、日志审计、协议转换和灰度分流。

**和 Nginx 的区别**：Nginx 是高性能反向代理 / Web 服务器，擅长静态资源、四层七层转发与基础限流；API 网关是在此之上叠加**业务级横切能力**（认证、租户识别、按 API 限流、审计、动态路由、插件热加载）。生产常见两层结构：边缘 Nginx/LVS 扛流量，内层网关做业务治理。代价是多一跳延迟，以及网关自身成为必须做高可用的关键点。

### 11. 网关有哪些核心职责？★★★【公认】

> 母版 #15　｜　岗位：`S+A`

**答**：统一入口与动态路由、认证鉴权、限流、熔断降级、灰度/权重分流、协议转换、日志与链路追踪（TraceID）、黑白名单与签名验签。

**加分**：强调"网关做粗粒度、服务做细粒度"——网关校验 Token 与租户，业务服务仍要校验数据权限，防止绕过网关直接打内部服务（配合 NetworkPolicy / mTLS）。

### 12. 四种限流算法怎么对比？网关该选哪个？★★★【公认】

> 母版 #17　｜　岗位：`S`

| 算法 | 机制 | 允许突发 | 特点 |
|---|---|---|---|
| 固定窗口 | 固定区间计数，到期清零 | 边界可能 2 倍突刺 | 最简单，精度差 |
| 滑动窗口 | 细分小格滚动统计 | 较平滑 | 精度高，内存/计算略高 |
| 漏桶 | 请求入桶、恒定速率流出 | ❌ 强制匀速 | 保护下游最稳，突发被丢 |
| 令牌桶 | 恒速发令牌，取到才放行 | ✅ 用存量令牌应对突发 | 网关最常用 |

**选型**：面向用户的接口用令牌桶（体验好、能吃短时峰值）；对脆弱下游或内部调用用漏桶/固定窗口严格限速。**别把漏桶和令牌桶的突发能力答反，这是整题归零的错误。**

### 13. 限流、熔断、降级有什么区别？★★★【公认】

> 母版 #20　｜　岗位：`S`

**答**：限流是**主动**按速率拒绝超额请求，保护自己不被打垮；熔断是**被动**发现下游持续失败后主动切断调用，防止级联故障；降级是熔断或异常发生后的**兜底动作**（返回缓存、默认值、关闭非核心功能）。限流在入口，熔断可同时在网关和服务内，降级通常要贴合业务语义、放在服务内实现。

### 14. 网关自己怎么避免成为单点？★★【公认】

> 母版 #21　｜　岗位：`S`

**答**：多副本无状态部署 + 前置负载均衡；会话状态外置（Redis / JWT），配置集中存储并支持热更新；自身也要限流（"宁可拒绝也不能让自己先崩"）；按 CPU、P99、QPS、限流命中、熔断次数做监控告警。放在 K8s 里就是多副本 Deployment + Service + 反亲和/PDB。

### 15. 网关如何与注册中心配合做动态路由？★★【官方 + 公认】

> 母版 #22　｜　岗位：`S+A`

**答**：网关不写死后端 IP，而是订阅注册中心的服务与实例列表，为每个服务生成上游集群；实例上下线时上游自动更新，路由规则本身指向"服务名"而非地址。以 Higress 的 `McpBridge` 为例：`type: nacos3` 声明服务来源，`nacosNamespaceId` / `nacosGroups` 限定订阅范围，`nacosRefreshInterval` 控制刷新间隔（默认 30 秒）。

⚠️ **关键区分**：服务发现自动生成的是**上游（后端集群）**，**不等于自动生成对外 HTTP 路由**；对外路由仍需 Ingress / 路由规则，或 MCP 场景下的专门开关（见本册 #43）。

### 16. 灰度发布有哪些策略？区别是什么？★★★【公认】

> 母版 #23　｜　岗位：`S`

| 策略 | 做法 | 回滚 | 代价 |
|---|---|---|---|
| 蓝绿 | 两套完整环境，一次性切流 | 秒级切回 | 双倍资源 |
| 金丝雀/灰度 | 新版本先接小比例流量，逐步放量 | 把比例调回 0 | 新旧并存、排障复杂 |
| A/B 测试 | 按用户特征分流，验证业务效果 | — | 周期长，看业务指标 |
| 影子流量 | 复制真实流量到新版本、不返回给用户 | 无风险 | 需要流量复制与数据隔离 |

**加分**：A/B 关注业务指标（转化率），金丝雀关注技术指标（错误率、P99）；K8s 环境里金丝雀比蓝绿更容易落地（Ingress/Gateway API 原生支持权重），蓝绿常要改 Service selector 或依赖服务网格。

## 第三篇　Kubernetes 与集群网络（#17–#23）

> Service / DNS / 探针是第四篇排障题的地基。#20（跨命名空间与外部域名解析）是两岗共用高频，也是真实集成里最常炸的一处。

### 17. Service 解决什么问题？为什么不能硬编码 Pod IP？★★★【公认 + 官方】

> 母版 #27　｜　岗位：`S`

**答**：Pod IP 是临时的，重建/迁移后必变。Service 按 label selector 选中一组 Pod，提供一个**稳定的虚拟 IP（ClusterIP）和 DNS 名**，kube-proxy 在节点上把访问 ClusterIP 的流量改写到后端 Pod IP，调用方因此感知不到 Pod 变化。

**加分**：后端列表由 Endpoints / **EndpointSlice**（新版，可扩展性更好）维护；Ingress 的 503 常因为 readiness 探针失败导致后端列表为空。

### 18. ClusterIP / NodePort / LoadBalancer 有什么区别？★★★【公认】

> 母版 #28　｜　岗位：`S`

**答**：**逐层叠加**：ClusterIP 只在集群内可达（东西向流量默认）；NodePort 在每个节点开 30000–32767 的静态端口转发到 ClusterIP；LoadBalancer 向云厂商申请外部 VIP，底层仍包含 NodePort + ClusterIP。另有 `ExternalName`（CNAME 到外部域名）和 headless Service（`clusterIP: None`，DNS 直接返回各 Pod IP，配合 StatefulSet 用）。

### 19. `name.namespace.svc.cluster.local` 到底解析成什么？★★★【官方 + 公认】

> 母版 #29　｜　岗位：`S`

**答**：CoreDNS 为 Service 提供 A/AAAA 记录，解析成 **Service 的 ClusterIP**（不是某个 Pod IP）；真正选 Pod 是后续 kube-proxy 转发时发生的。每个 Pod 的 `/etc/resolv.conf` 由 kubelet 配好 search 域，所以同命名空间内可只写短名 `name`，跨命名空间至少要写 `name.namespace`。headless Service 例外，DNS 返回各 Pod IP。

**加分**：环境变量 `*_SERVICE_HOST` 只在 Pod 启动时注入，**对之后新建的 Service 是过期的**，所以优先用 DNS。

### 20. 为什么跨命名空间用短域名会报 `Could not resolve host`？★★★【经验｜极高频排障题】

> 母版 #30　｜　岗位：`S+A`

**答**：短名只在**当前命名空间**的 search 域下补全；目标 Service 在别的命名空间时，必须写 `name.namespace` 或完整 FQDN `name.namespace.svc.cluster.local`。另一种常见原因是这个域名是**外部自定义域名**（如网关对外域名），CoreDNS 里根本没有对应记录 —— 此时要么配集群内 DNS，要么用 `hostAliases`（写 `/etc/hosts`）指向目标 IP。

⚠️ **加分/避坑**：`hostAliases` 对普通应用容器（读 `/etc/hosts`）有效，但 **Envoy 走 c-ares 解析、不读容器 hosts 文件**，给网关 Pod 打 hostAliases 通常无效。另外改 Deployment 模板会触发滚动重启，且 `hostAliases` 是数组，patch 时整体覆盖容易把已有条目弄丢——先查再改。

### 21. Ingress 资源 apply 了却不生效？★★【公认】

> 母版 #31　｜　岗位：`S`

**答**：Ingress **只是一组规则声明**，必须有正在运行的 **Ingress Controller**（nginx-ingress、Traefik、Higress 等）读取规则并配置真正的代理；新集群没装 Controller 时，规则静静躺着不生效。其次检查 `ingressClassName` 是否匹配、后端 Service 名/端口是否正确、以及是否有健康的 Endpoints。

### 22. 三种探针有什么区别？和 Service 有什么关系？★★★【官方 + 公认】

> 母版 #33　｜　岗位：`S`

**答**：
- `startupProbe`：启动慢的应用用它挡住其他探针，避免还没起来就被杀。
- `livenessProbe`：失败则**重启容器**，用于自愈死锁。
- `readinessProbe`：失败则把 Pod 从 Service 的**后端列表移除**（不重启），用于"暂时别给我流量"。

**高频追问**：接口偶发 503 / `no healthy upstream`，先看 readiness 是不是把 Pod 全摘了；把 liveness 配得过于敏感会导致"越重启越起不来"。

### 23. ConfigMap 和 Secret 的区别？★★【公认】

> 母版 #34　｜　岗位：`S`

**答**：两者都是键值对，可挂载为卷或注入环境变量。ConfigMap 明文存配置；Secret 存凭据，默认只是 **base64 编码，不是加密**，需开启静态加密、收紧 RBAC，生产常接外部 KMS / Sealed Secrets。优先用卷挂载而非环境变量，减少在进程列表和崩溃转储里泄露；卷挂载内容可由 kubelet 周期性同步更新（有延迟，且用 `subPath` 挂载不会更新），环境变量注入的则完全不会自动更新。

## 第四篇　通用排障：按现象分层收敛（#24–#28）

> 五题全是两岗共用 `S+A`，优先级最高。面试讲**排查顺序**比背结论得分高：先判故障域（DNS / 路由 / 鉴权 / 上游 / 应用），再说「请求是谁发出的」，最后讲怎么验证与防复发。

### 24. 应用报 `Could not resolve host`，怎么定位？★★★【经验】

> 母版 #53　｜　岗位：`S+A`

**答**：按顺序排除四层：① **名字写对没有**（跨命名空间要 `name.namespace`，外部域名要完整 FQDN）；② 这个域名是集群内 DNS 记录还是外部自定义域名 —— 外部域名 CoreDNS 不认识是常态；③ 从**实际发起请求的那个 Pod** 里测（`getent hosts` / `nslookup`），别在跳板机上测；④ 若需临时解析，用 `hostAliases` 指向目标 IP，但记住 Envoy/c-ares 不读 hosts。

**加分**：说明"请求到底是谁发出的"经常被忽略 —— 例如平台后端 Pod 代用户发请求，那么要修的是**那个 Pod** 的解析，而不是网关或浏览器。

### 25. `503 no healthy upstream` 说明什么？★★【经验】

> 母版 #54　｜　岗位：`S+A`

**答**：**网关活着、路由也匹配上了，但后端没有健康实例**。查：注册中心健康实例数是否为 0、readiness 探针是否把 Pod 全摘了、实例 weight 是否为 0、注册的 IP 是否是纯 IP（而非 URL）、网络策略是否放通。它和「连接超时」不同：超时通常是网络/DNS 不通。

### 26. 网关返回 404，可能有哪些原因？★★【经验】

> 母版 #56　｜　岗位：`S+A`

**答**：① 路由根本没生成（白名单/分组没订阅到、服务名大小写或版本后缀不一致）；② `Host` 头不在允许暴露的域名列表里；③ 路径前缀拼错（对外路径常常**不带**后端路径，后端路径由网关转发时自己拼）；④ 服务名冲突或路由被更精确的规则覆盖；⑤ 后端返回了 404 被透传。区分方法：把 404 的响应体和服务端访问日志对起来看，判断是网关产生的还是后端产生的。

### 27. 实例明明注册成功了，消费者却查不到，排查顺序？★★★【官方 + 经验】

> 母版 #57　｜　岗位：`S+A`

**答**：按 Nacos 官方口径查四项 —— `enabled` 是否被人工禁用、`healthy` 是否为 false、cluster 过滤是否不匹配、**保护阈值**是否触发导致返回的是"保护视图"。再往外查：`namespaceId` 填的是不是 ID 而不是名称、`groupName` 是否一致（默认 `DEFAULT_GROUP`）、订阅方是否订阅了正确的分组、以及服务类型（临时/持久）是否混用。

### 28. 改了配置却"看起来没生效"，常见的三个原因？★★【经验】

> 母版 #58　｜　岗位：`S+A`

**答**：① 改错了层级（改了注册中心的协议类型，但消费方读的是另一套装配逻辑）；② 数组型配置是**整体替换**，patch 时下标算错改到了别的对象 —— 改完必须回读确认；③ 有刷新周期或缓存（服务发现刷新间隔、客户端本地缓存、控制台列表不展示自动生成的路由），要等一个周期并用请求验证，而不是盯着界面。

## 第五篇　MCP 协议基础（#29–#38）

> 十题全为 AI 平台必会。按 `initialize` → `tools/list` → `tools/call` 的真实调用顺序背；#38 是 2026-07-28 新规范加分题，答题时**先主流 2025、再补新版**。

### 29. 什么是 MCP？解决什么问题？★★★【官方 + 公认】

> 母版 #37　｜　岗位：`A`

**答**：MCP（Model Context Protocol）是模型与外部工具/数据之间接入的开放标准。它解决 **M×N 集成爆炸**：过去 M 个 AI 应用对接 N 个工具要写 M×N 套适配，有了统一协议后各写一次，复杂度降为 **M+N**，常被称为"AI 应用的 Type-C 接口"。能力可跨应用、跨模型复用。

### 30. MCP 的核心架构有哪几部分？★★★【公认】

> 母版 #38　｜　岗位：`A`

**答**：Host（宿主应用，承载 AI 应用并管理会话）、MCP Client（与 Server 建连、发请求）、MCP Server（暴露工具/资源/提示词）、以及 LLM（理解意图并决定调用哪个工具）。Client 与 Server 一对一连接，Host 可同时管理多个 Client。

### 31. MCP 和 Function Calling 有什么区别？★★★【公认】

> 母版 #39　｜　岗位：`A`

**答**：**互补而非替代**。Function Calling 是模型侧能力，让模型输出结构化的"工具名 + 参数"，解决"模型如何表达想调什么"，但不负责发现和传输；MCP 是协议层标准，标准化工具的发现、描述、调用与传输，解决"工具怎么统一接入、跨应用复用"。MCP Server 暴露的工具经 Host 注入后，仍由模型通过 Function Calling 决策调用。

### 32. MCP 底层协议是什么？有哪些核心方法？★★【官方】

> 母版 #40　｜　岗位：`A`

**答**：基于 **JSON-RPC 2.0**，消息分请求 / 响应 / 通知三类，UTF-8 编码。常见方法：`initialize`（握手与能力协商）、`tools/list`、`tools/call`、`resources/list`、`resources/read`、`prompts/list`、`prompts/get`、`ping`（2025 时代）。

### 33. Tools / Resources / Prompts 三大原语的区别？★★★【公认】

> 母版 #41　｜　岗位：`A`

| 原语 | 是什么 | 副作用 | 谁控制 |
|---|---|---|---|
| Tools | 可执行的动作 | 有（写数据、调 API） | **模型**决定何时调用 |
| Resources | 只读的数据/内容 | 无 | **应用 / 用户**主动喂给模型 |
| Prompts | 预置提示词模板 | 影响输出方向 | **用户**显式选择 |

**加分**：记忆口诀 —— Tools 是模型主动去拿的能力，Resources 是应用主动给的数据，Prompts 是用户主动选的模板；三者交互模式不同，因此不能合并成一个原语。工具调用应当保留 human-in-the-loop 确认（官方规范 SHOULD 级要求）。

### 34. MCP 有哪些传输方式？怎么选型？★★★【官方】

> 母版 #42　｜　岗位：`A`

**答**（按 2025-06-18 规范）：**只定义两种标准传输** ——
- **stdio**：Client 把 Server 作为子进程启动，用 stdin/stdout 传换行分隔的 JSON-RPC 消息，**stdout 只能写 MCP 消息**，日志走 stderr。适合同机本地工具，零网络开销、天然隔离。
- **Streamable HTTP**：Server 独立进程，提供**单个 MCP endpoint** 同时支持 POST 与 GET。客户端每条消息是一个 POST，`Accept` 必须同时列出 `application/json` 和 `text/event-stream`；服务端可返回单个 JSON 对象，也可开 SSE 流返回多个消息。适合远程、多客户端、可水平扩展的场景。

**选型看部署边界**：同机 → stdio；跨机 → Streamable HTTP（接受网络开销 + 鉴权成本）。

⚠️ 旧版 `HTTP+SSE`（2024-11-05，两个端点：`GET /sse` 收消息 + `POST /message` 发消息）**已被 Streamable HTTP 取代、属于 deprecated**。很多面经还把它列为"三种标准传输"，可以按历史讲，但要说清它已被替代。

### 35. Streamable HTTP 有哪些必须知道的请求细节？★★【官方｜拉开差距】

> 母版 #43　｜　岗位：`A`

**答**：
- POST 请求体是**单条** JSON-RPC 请求/通知/响应；若输入是响应或通知且被接受，服务端返回 **202 无响应体**。
- 服务端对请求可返回 `application/json` 或 `text/event-stream`，客户端**两者都要支持**。
- 客户端 GET 该端点可开 SSE 流收服务端主动消息；不提供则必须返回 **405**。
- 会话 ID 是**可选的**：服务端可在 `InitializeResult` 响应里给 `Mcp-Session-Id`，之后客户端必须回带；显式结束用 `DELETE`，不支持返回 405。
- 后续 HTTP 请求必须带 `MCP-Protocol-Version` 头；缺省时服务端**应当假定 `2025-03-26`**；版本无效返回 400。
- **安全（SHOULD/MUST）**：校验 `Origin` 头防 DNS rebinding、本地运行时只绑 `127.0.0.1`、对所有连接做鉴权。

### 36. `initialize` 握手做了什么？★★★【官方，2025 时代】

> 母版 #44　｜　岗位：`A`

**答**：连接建立后、任何业务请求之前先握手：客户端声明自己支持的协议版本与 capabilities，服务端回应实际采用的版本与自身能力（如 `tools`、`resources`、`prompts`），完成**双向能力协商**；客户端随后发 `notifications/initialized` 表示就绪。客户端不支持服务端返回的版本时应断开。

**易错**：能力协商是**双向**的，不只是服务端单方面声明。

### 37. `tools/list` 和 `tools/call` 的报文长什么样？★★★【官方】

> 母版 #45　｜　岗位：`A`

**答**：
```json
{"jsonrpc":"2.0","id":1,"method":"tools/list","params":{}}
{"jsonrpc":"2.0","id":2,"method":"tools/call",
 "params":{"name":"get_time","arguments":{}}}
```
`tools/list` 返回工具定义数组，每个工具含 `name`、`description`、`inputSchema`（**JSON Schema**，用于声明并校验参数结构）、可选 `title` / `outputSchema` / `annotations`，支持 `cursor` 分页。`tools/call` 返回 `content` 数组与 `isError`。

**加分**：区分「协议错误」与「工具执行错误」——未知工具、参数非法是 JSON-RPC error（如 `-32602`）；工具内部业务失败应作为**正常结果**返回 `isError: true` 并给出模型能读懂、能据此纠正的错误描述。

### 38. 2026-07-28 版 MCP 规范改了什么？★★【官方｜加分题】

> 母版 #46　｜　岗位：`A`

**答**（重大变更，答出来能明显区分是否跟进新规范）：
- **MCP 变为无状态**：移除协议级 session 与 `Mcp-Session-Id`、移除 `initialize` / `notifications/initialized` 握手；每个请求在 `_meta` 里自带 `io.modelcontextprotocol/protocolVersion`、`clientCapabilities`，建议带 `clientInfo`。
- 新增 **`server/discover`**（Server MUST 实现），用于宣告支持的版本、能力与身份。
- 所有结果必须带 `resultType`（`complete` 或 `input_required`）；`tools/list` 等列表结果新增 `ttlMs` / `cacheScope` 便于缓存；工具列表**应当稳定排序**以命中 LLM prompt cache。
- HTTP POST 增加必填头 `Mcp-Method`、`Mcp-Name`；头与 body 不一致必须 400 拒绝（防网关按头鉴权、Server 按 body 执行的绕过）。
- 移除 SSE 断线续传（`Last-Event-ID`）；移除 `ping`、`logging/setLevel` 等；变更通知改走 `subscriptions/listen`。

**答题建议**：先答主流 2025 流程，再补一句"2026-07-28 起改为无状态、握手被移除，需要 `server/discover`"。**不要只背新版**，因为生产里绝大多数实现仍在握手时代。

## 第六篇　AI 平台与治理（#39–#46）

> 把协议落到平台：网关怎么暴露、怎么鉴权、注册中心与网关各管什么，最后两道是开放设计题。#39–#43 为两岗共用，#46 是运维侧灰度设计。

### 39. SSE 经反向代理/网关为什么会失败？★★【经验｜真实高频坑】

> 母版 #47　｜　岗位：`S+A`

**答**：旧 HTTP+SSE 传输在握手时会由服务端返回 `event: endpoint`，其 `data` 常是**绝对路径** `/message?sessionId=xxx`。客户端据此拼接后续 POST 地址，如果请求经过带路径前缀的网关（如 `/mcp-servers/<服务名>`），这个绝对路径会丢掉前缀，变成访问网关根路径 → 404 → 初始化失败、工具列表为空。Streamable HTTP 是单端点纯 POST、无 endpoint 发现过程，因此不存在该问题。

**加分**：这也是"为什么生产优先 Streamable HTTP 而非 SSE"最实在的理由；SSE 还有长连接与多副本下需要会话保持/共享状态的问题。

### 40. MCP Server 上生产要注意什么？★★★【公认】

> 母版 #48　｜　岗位：`S+A`

**答**：四个维度：
- **安全**：最小权限（只暴露必要工具）、远程传输鉴权（OAuth 2.1 / Bearer Token + TLS）、防提示词注入（工具返回值做无害化、敏感操作二次确认）、防 SSRF（工具内目标地址白名单）、返回值脱敏。
- **可靠性**：超时控制、写操作幂等（模型可能重试）、健康检查与自动重启、有状态操作外置存储。
- **上下文**：工具描述精简、结果分页/截断/摘要，避免撑爆上下文。
- **可观测**：每次工具调用记录 trace_id、参数、结果、耗时与失败率，保留审计日志。

### 41. 远程 MCP Server 怎么做鉴权？★★【公认 + 官方】

> 母版 #50　｜　岗位：`S+A`

**答**：本地 stdio 通常无需鉴权（子进程隔离本身就是边界，凭据从环境变量读）；远程 HTTP 必须鉴权。规范方向是 OAuth 2.1：MCP Server 作为资源服务器，客户端拿 access token 后每次请求携带；企业内部简单场景常用 API Key / Bearer Token，但安全性弱于 OAuth。原则：**每个请求独立校验**，不要把凭据或权限绑在会话状态上。

### 42. 什么是 MCP Registry / AI 网关？Nacos 3.x 与 Higress 各扮演什么角色？★★【官方】

> 母版 #51　｜　岗位：`S+A`

**答**：
- **Nacos 3.x** 同时是注册中心和 **AI Registry**（MCP / Prompt / A2A）：除实例（IP/端口/健康）外，还管理 MCP 服务名、版本、协议类型、工具清单与描述，并支持工具描述热更新、工具运行时开关、自动注册（Spring AI Alibaba / `NacosMCP` Python wrapper）。
- **Higress** 作为 AI 网关，订阅注册中心的服务与 MCP 元数据，把 MCP Server 统一暴露成 HTTP 接入点，并在网关层做鉴权、限流、审计与观测。官方 `McpBridge` 中 `enableMCPServer: true`（**目前仅支持 `nacos3` 类型**）、`mcpServerBaseUrl` 是统一路径前缀、`mcpServerExportDomains` 限定允许暴露的域名（不填表示全部域名）。

⚠️ **【实现】`allowMcpServers` 白名单**：Higress 官方字段表里**没有列出**这个字段，但源码 `api/networking/v1/mcp_bridge.proto` 有、实际集群配置里也存在并生效，语义是"只有白名单内的 MCP 才会被自动暴露成路由"。答题时说明这是实现中的安全边界，别当成文档明载的标准字段。

### 43. 「注册中心自动发现」和「网关自动生成路由」是一回事吗？★★【官方 + 经验｜易错】

> 母版 #52　｜　岗位：`S+A`

**答**：**不是**。传统服务发现自动生成的是**上游集群**（网关知道后端有哪些健康实例），**不会自动生成对外 HTTP 路由**；要对外访问仍需 Ingress / 路由规则。MCP 场景是特例：开启 `enableMCPServer` 后，网关订阅 MCP 元数据，才会按服务名自动铺出 `<前缀>/<服务名>` 这样的对外路径。官方还明确：**这类自动生成的路由不会出现在控制台的路由配置列表里**，只能用请求验证。

### 44. 能看到工具列表，但工具调用失败，怎么分层定位？★★★【经验｜很能区分水平】

> 母版 #55　｜　岗位：`A`

**答**：关键是认识到**「工具列表」和「实际连接」可能来自两条独立路径**。列表可能来自注册中心的元数据快照，而调用走的是连接点配置（transport + url）。所以按层查：
1. 连接点里的 `url` 是否非空、`transport` 是否与实际协议一致（例如被错误固定成 `stdio` 却只有 HTTP 服务）；
2. 从**真正发起调用的 Pod** 内 curl 该 url，看能否拿到 `initialize` 的 `serverInfo`；
3. 返回 404 查路由/路径前缀，403 查鉴权与 Host，DNS 错误查解析；
4. 最后才看工具本身的参数与实现。

**加分**：明确说"列表显示 3 个工具，不能证明客户端连通过后端"，这是很多集成问题的根因。

### 45. 设计一个多团队共用的 MCP 平台，你会怎么分层？★★【经验】

> 母版 #59　｜　岗位：`A`

**答**：分四层作答 ——
1. **注册与元数据**：MCP Server 用 SDK 自注册（连工具清单一并上报），或用 CI 推送元数据；实例生命周期交给 K8s Service 同步 / sidecar，避免幽灵实例。区分「实例数据」与「MCP 元数据」两套模型。
2. **网关**：统一域名 + 按服务名前缀暴露，统一鉴权（消费者粒度）、限流、审计；优先 Streamable HTTP。
3. **治理**：版本用不同服务名/路径区分，按产品/订阅者授权实现人群灰度；工具描述热更新与工具开关不重启生效。
4. **可观测与高可用**：每次调用 trace_id、工具级成功率与 P99、注册实例健康数告警；网关与注册中心多副本。

**加分**：主动说明哪一层的数据必须人工声明（工具 schema 注册中心猜不出来），以及哪些能力依赖具体版本（如 Nacos 3.3 的草稿/审核/发布）。

### 46. 设计一套灰度发布方案？★★★【经验】

> 母版 #60　｜　岗位：`S`

**答**：① **分流**：按用户 ID 取模或白名单保证同一用户体验一致；网关按权重/Header 路由，或注册中心打 `version` 元数据由负载均衡选择；② **节奏**：1% → 5% → 20% → 50% → 100%，每档观察 ≥10 分钟并覆盖高峰，盯 5xx、P99、CPU、下游错误率；③ **回滚**：把灰度比例调 0 或切回旧 Service selector，秒级完成；④ **数据兼容**：只加字段不删、缓存 key 带版本、幂等键语义不变、schema 变更分两阶段；⑤ **可观测**：按版本维度拆指标，否则新旧混在一起看不出问题。

# 附录 C　面试官最爱追问的"反常识"结论

1. 设了 `weight` 不等于按权重分流（Nacos 不保证消费者行为）。
2. 保护阈值返回的不健康实例，**不是真的健康**。
3. 同一 Nacos Service 下**不能混用**临时与持久实例。
4. 注册中心全挂，已有调用短时仍能通（靠本地缓存），只是不再感知变化。
5. 漏桶**不允许**突发、令牌桶**允许**突发，答反直接扣分。
6. 网关统一鉴权后，业务服务**仍要**做细粒度授权。
7. Ingress 资源本身不干活，必须装 Controller。
8. `readinessProbe` 失败只摘流量**不重启**，`livenessProbe` 失败才重启。
9. `Could not resolve host` 要在**真正发起请求的 Pod** 里测，跳板机测不算。
10. MCP 的 `tools/list` 能返回工具，**不代表**客户端与后端握手成功。
11. 旧 HTTP+SSE 已被 Streamable HTTP 取代，不是并列的第三种标准传输。
12. 2026-07-28 起的 MCP **没有 `initialize` 握手**，但仍要先答主流 2025 流程。
13. 服务发现自动生成的是**上游**，不是对外路由；MCP 自动暴露是特例。
14. Higress 自动生成的 MCP 路由**不会显示在路由配置列表**里。
15. `secret` 默认只是 base64 编码，**不是加密**。
