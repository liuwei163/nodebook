# DeepSeek-32B 推理性能实测报告

> 环境：离线 K8s（KCS）+ kthena + 昇腾 910B × 8（单节点） + vllm-ascend v0.22.1rc1  
> 部署形态：PD 分离，prefill TP=4 + decode TP=4  
> 测试时间：2026-10-30 ~ 2026-11-02  
> 压测工具：`04-推理性能实测/04-npu_bench.py`（纯标准库，流式请求，测 TTFT/TPOT/吞吐）

---

## 一、一句话结论

**去掉 decode 侧的 `--enforce-eager` 后，TPOT 从 146.5ms 降到 22.6ms（提升 6.5 倍），TTFT 从 340ms 降到 173ms，峰值吞吐从 82 提升到 214 tok/s。**  
**瓶颈随即从 decode 转移到 prefill —— 这暴露了 PD 分离 1:1 切分的配比失衡问题。**

---

## 二、先搞清楚几个概念（这是读懂后面数据的前提）

### 2.1 一个请求的时间被切成两段

```
请求发出 ──[ 读你的问题 + 排队 ]──> 第一个字 ──[ 一个字一个字写 ]──> 最后一个字
              └── TTFT ──┘                      └── 输出字数 × TPOT ──┘
              └──────────────── E2E 总耗时 ────────────────┘
```

- **TTFT（首字延迟）** = 排队 + 把输入读一遍（prefill）
- **TPOT（每字间隔）** = 写下一个字要多久（decode）
- **E2E** = TTFT + 输出字数 × TPOT

### 2.2 三个容易混的长度概念

| 概念                          | 指什么              | 谁来限制                        |
| --------------------------- | ---------------- | --------------------------- |
| **输入长度**（prompt tokens）     | 你发给模型的那段话有多长     | 业务决定                        |
| **输出长度**（completion tokens） | 模型要生成多少字         | 业务决定 / `max_tokens`         |
| **上下文长度**（context length）   | 输入 + 输出 的**总上限** | 部署参数 `--max-model-len 8192` |

**关键理解**：上下文长度是"天花板"，不是"每次都用满"。

同样是 8192 的上下文窗口，一次请求可以是：

- `4000 输入 + 32 输出`（长输入短输出）
- `44 输入 + 128 输出`（短输入长输出）
- `8000 输入 + 192 输出`（顶满窗口）

**两种请求对系统的压力完全不同，因为压力落在了不同的硬件环节上。**

### 2.3 打个比方：读书 + 写作文

把模型想成一个人，桌上摊着资料，手里握着笔：

|                        | 干什么        | 累在哪                | 对应指标       |
| ---------------------- | ---------- | ------------------ | ---------- |
| **长输入**（4000 token 资料） | 读 4000 字资料 | **读得慢**，要先全部读完才能动笔 | TTFT 高     |
| **短输入**（44 字问题）        | 瞄一眼问题      | 几乎不花时间             | TTFT 低     |
| **长输出**（500 字作文）       | 写 500 个字   | **写得慢**，一笔一笔写      | TPOT × 500 |
| **短输出**（32 字回答）        | 写一句话       | 很快                 | TPOT × 32  |

所以：

- **长输入短输出**（RAG、文档问答、摘要）→ 瓶颈在"读"，看 **TTFT**
- **短输入长输出**（聊天、写作、代码生成）→ 瓶颈在"写"，看 **TPOT**
- **长输入长输出**（长文档翻译）→ 两头都慢，两个都要看

**这也是为什么我在压测脚本里内置了两个场景**：

- `long-in`：5700 字输入 / 32 字输出 → 模拟"读长资料答一句话"
- `short-in`：44 字输入 / 128 字输出 → 模拟"看一眼问题写一段话"

## 四、三个关键发现

### 发现 1：`--enforce-eager` 是 decode 慢的元凶

**现象**：TPOT 146.5ms，而理论值应该是 10~25ms（每卡读取 16.3GB 权重 ÷ 1.6TB/s ≈ 10ms + 通信）。

**原因**：`--enforce-eager` 禁用了昇腾的 ACL Graph（图模式）。图模式会把一连串小算子合并成一张图一次性下发，而 eager 模式每个算子都要单独调度一次。decode 阶段每生成一个字要跑几百个算子，**调度开销累加起来就是那 120ms 的差值**。

**证据**：移除后 TPOT 直接落到 22.6ms，与理论值吻合。

**副作用**：TTFT 也从 340ms 降到 173ms——说明图模式对首 token 生成同样有优化，之前那 340ms 的"PD 固定开销"里，约有一半其实是 eager 造成的。

### 发现 2：真实瓶颈是 prefill，不是 decode

改造后 decode 变得很健康（TPOT 全程 22~25ms，不抖动），但真实输入场景下：

| 并发 | TTFT   | 推算的排队时间 |
| -- | ------ | ------- |
| 1  | 451ms  | 无排队     |
| 4  | 876ms  | ~400ms  |
| 8  | 2126ms | ~1.7s   |

8 个请求 × 4000 token = 32000 token，prefill 吞吐约 15000 tok/s，算完需要 2.1 秒 —— 与实测的 2126ms 完全吻合。

**结论：prefill 没有故障，它是满负荷了。TTFT 线性上涨是排队，不是性能退化。**

### 发现 3：PD 分离 1:1 切分配比失衡

|         | 卡数 | 状态                    |
| ------- | -- | --------------------- |
| prefill | 4  | **满负荷**，8 并发排队 2 秒    |
| decode  | 4  | **闲置**，TPOT 22ms 从未抖动 |

对"长输入短输出"的负载来说，这个切分是浪费的：**一半算力锁在 decode 上，而 decode 根本用不完。**

这直接导出一个待验证的假设：

> **共置 TP8（8 卡全给一个实例）在长输入场景下应优于 PD 4+4**，因为能让 8 卡全部参与 prefill。预期 TTFT 改善 30% 以上（TP8 的 prefill 效率约为 TP4 的 1.3~1.4 倍，不是 2 倍，通信开销吃掉一部分）。

## 五、按业务场景选配置

### 5.1 场景 → 瓶颈 → 看什么指标

| 业务场景        | 输入       | 输出       | 瓶颈          | 主看指标        | 优化方向                     |
| ----------- | -------- | -------- | ----------- | ----------- | ------------------------ |
| RAG 问答、文档摘要 | 长（2k~8k） | 短（几十~几百） | **prefill** | TTFT p99    | 提高 prefill 算力、减少输入、开前缀缓存 |
| 客服对话        | 短        | 短        | 均衡          | TTFT + TPOT | 通用配置即可                   |
| 写作、代码生成     | 短        | 很长（1k+）  | **decode**  | TPOT        | 提高 decode 算力、大 batch     |
| 长文档翻译       | 长        | 长        | 两头都紧        | TTFT + TPOT | 加卡，或拆成两阶段                |
| 离线批处理、数据标注  | 任意       | 任意       | **吞吐**      | tok/s       | 大 batch、忽略延迟、可降精度        |

### 5.2 本次环境实测出的容量

| 场景              | 健康并发上限  | 峰值吞吐        | 依据                      |
| --------------- | ------- | ----------- | ----------------------- |
| 长输入（4000 token） | **4~8** | 83.8 tok/s  | 并发 8 时 TTFT 已到 2.1 秒    |
| 短输入（≤128 输出）    | **16+** | 508.9 tok/s | 并发 16 时 TPOT 仍 27.4ms   |
| 长输入但全命中缓存       | 8       | 214.0 tok/s | 并发 16 时 TPOT 劣化到 65.8ms |

### 5.3 关键参数说明

| 参数                           | 当前值                        | 说明                                 |
| ---------------------------- | -------------------------- | ---------------------------------- |
| `--tensor-parallel-size`     | 4                          | 模型切片数，越大每卡权重越少、KV 空间越大，但通信开销递增     |
| `--max-model-len`            | 8192                       | **上下文长度天花板**（输入+输出），决定单个请求最多占多少 KV |
| `--gpu-memory-utilization`   | prefill 0.85 / decode 0.95 | 显存占比，扣掉权重后剩下的给 KV 池                |
| `--max-num-batched-tokens`   | 16384                      | 单批能塞多少 token，影响 prefill 吞吐         |
| `--max-num-seqs`             | 未设（默认 256）                 | 同时处理多少请求，实际受 KV 容量限制               |
| `--enforce-eager`            | **已移除**                    | 曾禁用图模式，是 TPOT 慢的元凶                 |
| `--no-enable-prefix-caching` | decode 端关闭                 | 前缀缓存，decode 端关掉是合理的                |

### 5.4 环境实测出来的容量富裕度

decode 端日志显示：

```
Available KV cache memory: 39.92 GiB    （每张卡）
```

4 卡合计约 160 GiB。32B 模型（GQA，8 个 KV head）每 token 约 256KB，折算总容量约 **65 万 token**，按 8192 上下文能撑 **约 80 倍并发**。

**结论：KV 不是瓶颈，抢占次数 0。** 真正的约束是 prefill 算力。

## 六、踩过的坑

| 坑                               | 现象                                | 解法                                       |
| ------------------------------- | --------------------------------- | ---------------------------------------- |
| 压测脚本的 prompt 全部相同               | TTFT 异常低（280ms），且长短输入几乎一样         | 在 prompt **最前面**加随机串打散前缀缓存；必须放最前面，放末尾不生效 |
| 重复测量波动大                         | 同配置两次跑 TTFT 差 23%                 | 每个配置跑 3 次取中位数，报告里带上波动范围                  |
| 只跑 max_tokens=512 的短输入场景        | 单次压测要 1 小时（TPOT 146ms 时）          | 按 `E2E = TTFT + 字数 × TPOT` 预估耗时，先跑小样本    |
| port-forward 刷 connection reset | 日志满屏红字                            | 客户端读完响应体再关闭，请求头加 `Connection: close`     |
| 查抢占查错 Pod                       | 查了 prefill 而不是 decode             | prefill 不长期持有 KV 池，抢占只会出现在 decode 端      |
| 用 tok/s 判断体验                    | 103 tok/s 看着不错，实则每个用户只有 6.4 tok/s | 用 TPOT 判断单用户体验，用 tok/s 判断总产能             |

## 七、下一步待办
