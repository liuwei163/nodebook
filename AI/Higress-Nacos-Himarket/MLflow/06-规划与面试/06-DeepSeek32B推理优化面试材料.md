# DeepSeek-32B 推理性能优化：面试材料

> 一份可以直接复述的项目叙事，含数据、方法论和可能的追问。
> 场景：离线 K8s（KCS）+ 昇腾 910B × 8（单机）+ kthena + vllm-ascend v0.22.1rc1

---

## 一、30 秒版本（自我介绍时用）

> 我在离线 Kubernetes 环境里负责大模型推理平台，用 kthena 部署了 DeepSeek-32B。上线后发现生成速度只有 6.9 tok/s，用户反馈"卡"。排查定位到 `--enforce-eager` 参数禁用了昇腾的图模式，移除后 TPOT 从 146.5ms 降到 22.6ms，提升 6.5 倍。
> 修复后又用对比实验验证了部署架构：原本的 PD 分离在这个负载下是负优化，改成共置 TP8 后，首字延迟降低 45%、吞吐提升 37%。

## 二、完整叙事（3 分钟版本）

### 2.1 背景

- 离线/内网 K8s 集群（移动云 KCS），8 张昇腾 910B 绑在单节点
- 已有 DevOps 底座：Harbor、GitLab、ArgoCD、Higress
- 用 kthena（Volcano 社区的 K8s 原生 LLM 推理平台）部署 DeepSeek-R1-Distill-Qwen-32B
- 初始形态：**PD 分离**，prefill 4 卡 + decode 4 卡，用 Mooncake 做 KV 传输

### 2.2 问题：生成速度只有 6.9 tok/s

先写了个压测工具（纯 Python 标准库，离线环境装不了依赖），实测：

| 指标 | 实测值 | 理论预期 | 判断 |
|---|---|---|---|
| TPOT（每字间隔） | **146.5ms** | 10~25ms | 慢了 6~10 倍 |
| 单用户速度 | 6.9 tok/s | >30 tok/s | 比人阅读还慢 |
| TTFT（首字延迟） | 340ms | — | 正常 |

**关键判断**：TTFT 正常、TPOT 异常，说明问题 100% 在 decode 阶段，不在 prefill。

### 2.3 排查：三步定位

**第一步，用并发梯度排除排队因素。**

跑 1/4/8/16 四档并发，TPOT 分别是 144.7 / 147.1 / 146.6 / 149.2ms —— **几乎不动**。

如果瓶颈是排队，并发升高时 TPOT 应该明显上涨。它不动，说明**每个请求自己就是这么慢**，与竞争无关。

**第二步，用理论值反推。**

decode 是 memory-bound：每生成一个字，每张卡都要把自己那份权重读一遍。

- TP=4，32B 模型，每卡约 16.3GB 权重
- 昇腾 910B HBM 带宽约 1.6TB/s
- 理论读一次权重约 10ms + 通信开销 → 应该在 20~30ms

实测 146ms，**多出来的 120ms 不属于任何正常的 decode 计算**。

**第三步，看启动参数。**

decode role 里有 `--enforce-eager`。

### 2.4 根因：`--enforce-eager` 禁用了图模式

这个参数的作用是"不要用图模式，逐算子执行"。

- **默认（图模式）**：把几百个算子录成一张计算图，一次性下发，算子还能融合
- **eager 模式**：每个算子单独派发，无法融合

decode 时每生成一个字要跑 64 层 × 每层几个算子 ≈ 几百个算子。eager 模式下：
1. 每个算子都要 CPU 下发一次指令 → 累加几十毫秒
2. **算子融合失效** → 本该合并成一次算完的操作变成多次，中间结果反复读写显存

这两部分加起来就是那 120ms。

### 2.5 解决：移除参数

```diff
- --enforce-eager
```

单变量改动，重启后：

| 指标 | 改前 | 改后 | 提升 |
|---|---|---|---|
| TPOT | 146.5ms | **22.6ms** | 6.5 倍 |
| 单用户速度 | 6.9 tok/s | **36 tok/s** | 5.2 倍 |
| TTFT | 340ms | **173ms** | 2 倍 |
| 峰值吞吐 | 82 tok/s | **214 tok/s** | 2.6 倍 |

22.6ms 与理论值（10ms 读权重 + 通信）吻合，说明改动到位。

**意外收获**：TTFT 也从 340ms 降到 173ms。说明之前认为的"PD 移交固定开销 340ms"，其实有一半是 eager 造成的，真实的 PD 移交成本只有 150~200ms。

### 2.6 第二步排查：修完 decode，prefill 露出来了

decode 变快后重新压测，长输入场景出现新问题：

| 并发 | TTFT p50 | TPOT |
|---|---|---|
| 1 | 451ms | 22.4ms |
| 4 | 876ms | 24.0ms |
| 8 | **2126ms** | 24.9ms |

**TPOT 依然稳定，但 TTFT 在 8 并发时炸到 2.1 秒。**

**验证是不是 KV 不够**：

```bash
kubectl logs <decode-pod> | grep -icE "preempt|evict"
# 0 次
```

日志还显示 `Available KV cache memory: 39.92 GiB/卡`，4 卡共 160GB，按每 token 256KB 算，理论上能支撑 65 万 token、约 80 倍并发。

**结论：KV 完全够用，不是内存问题。**

**真正原因**：8 个请求 × 4000 token = 32000 token，prefill 吞吐约 15000 tok/s，算完需要 2.1 秒 —— 与实测 2126ms 完全吻合。

**prefill 没有故障，它是满负荷了。**

### 2.7 架构层面的发现：PD 配比失衡

把资源占用摊开看：

| | 卡数 | 状态 |
|---|---|---|
| prefill | 4 | **满负荷**，8 并发排队 2 秒 |
| decode | 4 | **闲置**，TPOT 22ms 从未抖动 |

**一半算力锁在 decode 上，而 decode 根本用不完。**

这导出一个可验证的假设：共置 TP8 让 8 卡都参与 prefill，应该全面优于 PD。

### 2.8 验证：共置 TP8 vs PD 分离

把 PD 改成单实例 TP=8（合并 role、删掉 KV 传输配置），用同一套压测参数对比。

**短输入（44 token 进 / 128 token 出）**

| 并发 | TTFT p50 | | TPOT | | 吞吐 tok/s | |
|---|---|---|---|---|---|---|
| | PD | **共置** | PD | **共置** | PD | **共置** |
| 16 | 514ms | **323ms** | 27.2 | **26.4** | 509 | **557** |
| 64 | 622ms | 624ms | 35.3 | **31.8** | 1542 | **1767** |
| 128 | 1188ms | **704ms** | 43.6 | **40.3** | 2222 | **2759** |

**长输入（4000 token 进 / 32 token 出）**

| 并发 | TTFT p50 | | TPOT | | 吞吐 tok/s | |
|---|---|---|---|---|---|---|
| | PD | **共置** | PD | **共置** | PD | **共置** |
| 1 | 451ms | **222ms** | 22.4 | 22.4 | 27.9 | **34.8** |
| 4 | 876ms | **734ms** | 24.0 | 27.8 | 73.9 | **88.4** |
| 8 | 2126ms | **1159ms** | **24.9** | 36.6 | 83.8 | **115.0** |

**结论：共置赢四场，PD 只赢一场。**

唯一 PD 占优的是"长输入高并发时的 TPOT"（24.9 vs 36.6ms）。原因是共置时 prefill 和 decode 抢同一批算力，长输入的 prefill 会把 decode 饿着。

但按 E2E 总耗时算（4000 输入 + 32 输出，8 并发）：

- PD：2126 + 32×24.9 = **2923ms**
- 共置：1159 + 32×36.6 = **2330ms**

**共置仍然快 20%**，因为 TTFT 省下的 1 秒远大于 TPOT 多花的 350ms。

### 2.9 最终选型

**采用共置 TP8。**

除了性能，还有运维理由：

| | 共置 | PD |
|---|---|---|
| 配置复杂度 | 一个 role | 两个 role + Mooncake + KV 端口段 |
| 故障点 | 少 | 多（KV 传输链路断了整条服务挂） |
| 扩容粒度 | 8 卡一跳 | 可单独扩 prefill |

对单机 8 卡的场景，共置的简洁性优势大于 PD 的弹性优势。

**PD 什么时候才值得用**：长输入为主 + 高并发 + 对出字流畅度极度敏感（比如实时字幕、语音对话），且有多余的 GPU 可以给 prefill 独立扩容。

## 三、方法论（面试最值钱的部分）

### 3.1 基线先行

没有基线就没有优化。"准确率 85%"不是信息，"比基线高 6.2 个点"才是。

具体做法：改任何配置之前，先把当前状态的完整指标跑一遍存下来，后面每次改动都拿同一套参数对比。

### 3.2 单变量原则

一次只改一个东西。这次两个阶段分别只改了：
1. 移除 `--enforce-eager`（其他参数全不动）
2. 改架构（PD → 共置，但确保压测参数完全一致）

如果同时改三四个参数，性能提升了也不知道是谁的功劳。

### 3.3 用理论值反推异常

TPOT 146ms 之所以能被判定为"异常"，是因为算过理论值：每卡读 16.3GB 权重 ÷ 1.6TB/s ≈ 10ms。

**没有理论值做参照，146ms 看起来只是个"不太好的数字"，而不是"明显的 bug"。**

### 3.4 用对比实验隔离变量

想搞清楚 TTFT 里哪些是"固定开销"、哪些是"prefill 计算"，用的是缓存对比：

| 跑法 | 结果 | 说明 |
|---|---|---|
| 每次请求前缀都不同（打散） | 643ms | 真实 prefill 全额付费 |
| 所有请求完全相同（全命中缓存） | 340ms | prefill 被跳过，只剩固定开销 |

**差值 303ms 就是 4000 token 的真实 prefill 成本**，剩下的 340ms 是排队 + 移交 + 首 token 调度。

这个手法很实用：**想拆解一个复合指标，就找到一个只影响其中一部分的开关。**

### 3.5 测量规范：重复 3 次取中位数

发现同一配置两次测量 TTFT 相差 23%（993ms vs 767ms）。

原因：服务端当时的 KV 占用、调度器状态、网络抖动都会影响。

所以：**每个配置至少跑 3 次，报中位数，并在报告里带上波动范围。**

写"TTFT 约 280ms"是虚的，写"TTFT p50 = 280ms（3 次测量 250~344ms）"才站得住。

### 3.6 区分突发流量和持续流量

同一套系统、同样 32 并发，TTFT 能差 2.5 倍：

| 参数 | 流量形态 | TTFT |
|---|---|---|
| 32 并发 + 32 个请求 | 32 个同时涌入（突发） | 825ms |
| 32 并发 + 256 个请求 | 持续有人进出（稳态） | 333ms |

**做容量规划前必须先确定业务是哪种形态**，否则数字会差一倍以上。

### 3.7 用 Goodput 而不是峰值吞吐

128 并发时吞吐 2759 tok/s，但 TTFT 已经 704ms、p99 1.1 秒。

**能交出去的容量不是峰值，而是"满足 SLA 前提下的最大吞吐"。**

定 TTFT p99 < 1.5 秒的门槛，那 128 并发可用（2759 tok/s），再往上就要重新评估。

### 3.8 不要用总吞吐判断体验

103 tok/s 看着不错，但如果那是 16 个用户分摊，每人只有 6.4 tok/s，仍然在忍受"一个字一个字蹦"。

**判断体验看 TPOT（单用户），判断成本看 tok/s（总产能），两者不能混。**

## 四、踩过的坑（体现实战经验）

> 原始出处与排查细节见《DeepSeek-32B-推理性能实测报告》第六章（本节为面试化改写）。

| 坑 | 现象 | 怎么发现的 | 怎么解决的 |
|---|---|---|---|
| 压测 prompt 全部相同 | TTFT 异常低（280ms），且长短输入几乎一样 | 输入量差 150 倍而 TTFT 只差 7%，不合常理 | 在 prompt **最前面**加随机串打散前缀缓存（放末尾无效，因为 prefix cache 按前缀匹配） |
| `--num-requests` 小于 `--concurrency` | 设了 64 并发但数据和 32 并发一样 | 对比两组数据发现吞吐几乎相同 | 请求数必须是并发数的 2~4 倍，脚本里加了告警 |
| 查抢占查错 Pod | 日志里搜不到 preempt | 想通了：prefill 不长期持有 KV，抢占只会出现在 decode | 查 decode 的 Pod 而不是 prefill |
| 单次 `max_tokens=512` 压测跑一小时 | 以为脚本卡死 | 算了一下：512 × 146ms = 74 秒/请求 × 32 个 | 按 `E2E = TTFT + 字数 × TPOT` 预估耗时，先跑小样本 |
| port-forward 日志刷 connection reset | 满屏红字，以为服务有问题 | 报错里的端口是客户端源端口，说明是客户端先断开 | 读完响应体再关连接，加 `Connection: close` 头 |
| 用 tok/s 判断体验 | 103 tok/s 觉得还行 | 拆开算每人只有 6.4 tok/s | 用 TPOT 判断单用户体验 |

## 五、可能的追问与回答

**Q：为什么 `--enforce-eager` 会让性能差 6 倍？**

它禁用图模式。decode 每生成一个 token 要跑几百个算子，eager 模式下每个算子单独派发，还有算子融合失效的问题——本该合并成一次算完的操作被拆成多次，中间结果反复读写显存。两部分加起来就是我们测到的 120ms 差值。

**Q：为什么不直接加卡解决？**

先算了一笔账：TP 从 4 加到 8，理论 decode 时间从 10ms 降到 5ms，只能省 5ms，而实际多出来的是 120ms。**加卡解决不了配置问题。** 而且当时的 8 张卡已经被 PD 两个 role 占满，没有空闲卡。

**Q：PD 分离不是很主流的方案吗，为什么你否掉了？**

PD 分离适合"长输入 + 高并发 + 对出字流畅度敏感"的场景，因为它能让 decode 不被 prefill 阻塞。但我的负载是短输入为主，PD 的收益（decode 不被干扰）用不上，反而要付两笔代价：KV 搬运导致 TTFT 升高（实测 8 并发时 2126ms vs 共置 1159ms），以及 1:1 的刚性切分让 decode 侧一半算力闲置。

**架构选型要看负载特征，不能看哪个"先进"。**

**Q：怎么确定压力测试的容量上限？**

三个信号同时看：
1. TTFT 开始偏离线性（排队出现）
2. TPOT 明显上涨（批处理效率下降）
3. 吞吐增速放缓甚至下降（超出容量）

我的数据里，短输入在 128 并发时才出现 TTFT p99 到 1.1 秒的迹象，长输入在 8 并发就已经排队 2 秒——**同一套机器，容量差 16 倍，因为瓶颈在不同环节**。

**Q：昇腾和 NVIDIA 在调优上有什么区别？**

主要三点：
1. 图模式在昇腾叫 ACL Graph，NVIDIA 叫 CUDA Graph，`--enforce-eager` 参数名一样，但底层实现和版本兼容性不同
2. 昇腾的图模式对 decode 提升特别大（小算子多），而且 v0.22.1 之后图模式还会做显存 profiling，实际可用显存比设定的少约 1.7%
3. 生态上昇腾的量化路径是 msmodelslim 出 W8A8，不像 NVIDIA 有成熟的 FP8/AWQ/GPTQ 工具链

**Q：如果让你继续优化，下一步做什么？**

三个方向，按投入产出排：
1. **调 `--max-num-batched-tokens`**：现在是 16384，prefill 一次吞太多导致长输入场景 decode 被饿（TPOT 36.6ms）。调到 4096 可能让 TPOT 降回 28ms 左右，代价是 TTFT 涨 10~15%。这是一个可以用数据找到平衡点的旋钮。
2. **量化**：昇腾上走 W8A8，显存减半后能支撑更大并发，但要先验证精度损失。
3. **LoRA 多租户**：一份 65GB 基座 + N 份 adapter，动态加载不重启，用 router 的 lora-affinity 做路由。

## 七、一句话总结（收尾用）

> **这次优化的核心不是"调了一个参数"，而是建立了一套"能定位问题、能验证结论"的方法：先用理论值判断异常，再用单变量实验隔离原因，最后用对照实验验证架构假设。** 一个参数带来 6.5 倍提升是运气好，但能算出它应该是 6.5 倍，才是能力。
